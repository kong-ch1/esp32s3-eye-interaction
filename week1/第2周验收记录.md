## 一、验收目标

第 1 周只能做到「板子推、网页看」。第 2 周要证明：

1. 网页能**让设备再采一次**，而不是只能看历史；
2. 这条链路的**每一段都有证据**：服务器受理 / 指令下发 / 设备接收 / 执行完成 / 超时；
3. 新采的数据能**精确关联**到触发它的那次请求，不靠时间窗口猜。

---

## 二、证据链实测（真机，非模拟）

指令 `CMD-20260918-0005`，参数：采 12 条、间隔 100ms。

| 阶段 | 服务器侧记录时刻 | 相对上一步 |
|---|---|---|
| ① 服务器受理 `issued` | 2026-09-18 **11:00:11.560** | — |
| ② 指令下发 `delivered` | 2026-09-18 **11:00:12.453** | +893 ms |
| ③ 设备接收 `received` | 2026-09-18 **11:00:12.879** | +426 ms |
| ④ 执行完成 `done` | 2026-09-18 **11:00:15.664** | +2785 ms |
| 端到端 | | **4104 ms** |

**各段耗时说明**：

- **受理 → 下发 893 ms**：板子每 1 秒才上报一次，指令搭在下一次上报的响应里，所以这段天然在 0~1000 ms 之间。这是本方案**有意为之的取舍**（见设计文档第 2 节），换来的是板子不必开监听端口、不必引入 MQTT。
- **下发 → 设备接收 426 ms**：一次 HTTP 往返（板子收到指令后立刻回报 `received`），含无线抖动。
- **接收 → 完成 2785 ms**：12 条 × 100 ms 间隔 = 1200 ms，加上 12 次 HTTP 上报的往返开销。

这条链上**每一段都是可测量的**，不是"点了一下，等一会儿，出来了"。

## 三、「刷新存储记录」与「触发新采集」的区别

这是本单元最容易含糊过去的地方，所以用**同一时刻的两次操作**直接对比：

| 操作 | 结果 |
|---|---|
| **刷新**（再次 `GET /api/latest`） | 还是同一条记录 `id=21906`、`seq=4`；库里仍是 **20883** 条；耗时 8 ms |
| **点「重新采集」**（`POST /api/command`） | 新增 **13** 条记录（`id 21908~21920`），全部带 `request_id=CMD-20260918-0005`；端到端 4104 ms |

刷新**一条都不会多**，下发指令才会多。这不是界面上的文案，是数据库里的行数。

## 四、数据层如何区分新采集与历史记录

新增两个字段，让"这条数据是谁触发的"成为**数据库里的直接关联**，而不是靠时间推断：

| 字段 | 定时上报 | 本次指令触发 |
|---|---|---|
| `trigger` | `'timer'` | `'command'` |
| `request_id` | `NULL` | `CMD-20260918-0005` |
| `cmd_state` | `NULL` | 首条 `received`、末条 `done`、中间 `NULL` |

本次指令触发的 13 条记录（首条与末条的回执标记可见）：

| 21910 | command | — | -0.0083 | -0.1199 | -1.0015 | 11:00:13 |

## 五、超时分支（服务器主动判定并留证）

超时不是"查的时候顺手算"，而是服务器后台看门狗**每秒扫一次并落库**，
所以超时这件事有服务器侧的时间戳。

实测（`tools/cmd_selftest.py --timeout-test`，发指令后故意不去取）：

```
request_id : CMD-20260918-0004
status     : timeout
created_at : 2026-09-18 10:51:42.258
timeout    : 2026-09-18 10:52:12.712（阶段=accept）
total_ms   : 30454
```

`timeout_stage` 区分两种完全不同的故障，验收时能一眼看出问题出在哪一段：

- **`accept`** —— 指令发出去了，板子一直没来取 → 板子掉线 / 重启 / 没在 上报
- **`exec`** —— 板子取走了，但没执行完 → 执行中崩了 / 上报通道断了

## 五之二、真实浏览器实测（2026-09-20 补测）

前面几节的验收都是用命令行脚本做的。网页部分此前只做过**静态**检查
（JS 语法、元素 id 一致性、接口连通性）和**离线**逻辑验证 —— 那些都证明不了
"在真实浏览器里点一下按钮，界面真的会动"。这一节补上。

**工具**：`tools/browser_test.py` —— 用 **Chrome 153 无头模式 + DevTools Protocol**

