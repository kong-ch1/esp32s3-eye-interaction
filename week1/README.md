# 第1—3周 运行说明 · 开发板传感采集 / 双向交互 / 实体按键

目标：真实传感器（IMU）→ ESP32-S3-EYE 采集 → **独立联网（WiFi）**传到自己的服务器 → 网页实时展示并验证；
再补上两条反向的交互通道 —— **远端网页能指挥设备**（第2周）、**现场的人按键也能触发**（第3周）。

当前状态：✅ **三周的功能全部真机验证通过**。板载加速度计（**QMA6100P**，原理图标注的 QMA7981 已停产换代，详见下方"型号勘误"）以 1Hz 通过 WiFi HTTP 上报；网页可下发指令让设备立刻再采一批；板上的四个实体键按下即可触发采集并在本地亮灯反馈。

> 部署说明：本组暂无 VPS，按任务卡"备用路径"以本地电脑（局域网 IP `10.1.41.18`）充当服务器，**VPS 部署待补**。板端为 WiFi 独立联网上传，非 USB 桥接（USB 串口仅用于看日志）。

## 接口

| 方法   | 路径                      | 说明                                                           |
| ---- | ----------------------- | ------------------------------------------------------------ |
| POST | `/api/data`             | 板端上传一条记录，字段：`device_id`(必填)、`seq`、`ts`、`ax/ay/az`、`gx/gy/gz`、`temp_c`、`free_heap`、`min_free_heap`、`total_heap`、`rssi`、`request_id`、`trigger`、`cmd_state`、**`button`**、**`press_delay_ms`**。**响应体里会捎带待执行的下行指令** |
| GET  | `/api/latest`           | 最新一条 + `age_seconds` + `stale`（是否超阈值）                        |
| GET  | `/api/history?limit=20` | 最近 N 条                                                       |
| GET  | `/api/devices`          | 出现过的设备及其最后上报时间、累计条数、容量上限                                     |
| GET  | `/api/export.csv`       | CSV 导出，可选 `limit=条数` / `hours=最近几小时` / `device_id=设备` |
| POST | `/api/command`          | **第2周**：下发「重新采集」指令，返回 `request_id`                          |
| GET  | `/api/command/<id>`     | **第2周**：查指令状态、四个时间点、各阶段耗时、新采集条数                            |
| GET  | `/api/commands?limit=N` | **第2周**：最近指令列表                                              |
| GET  | `/api/buttons?limit=N`  | **第3周**：实体按键事件，按 `request_id` 聚合成"一次按键一条"，含按键名、样本数、跨度、按下→采样延迟 |
| GET  | `/api/camera`           | 摄像头 MJPEG 视频流（服务器中转）                                     |
| GET  | `/api/camera/status`    | 中继状态（观看人数、帧龄、重连次数）                                 |
| GET  | `/`                     | 展示页面                                                         |

服务端额外记录 `server_ms`（收到时刻）和 `src_ip`（来源 IP）——这两个字段是"数据来自本组真实设备"的证据（板子 WiFi IP：`10.1.41.160`）。

`trigger` 有三个取值，把"这条数据是谁触发的"变成数据层可直接查的字段，而不是靠时间猜：

| 值 | 含义 | 同时带的字段 |
|---|---|---|
| `timer` | 板子自己按 1Hz 上报 | — |
| `command` | 网页点「重新采集」下发的指令产生 | `request_id='CMD-…'`、`cmd_state` |
| `button` | **现场有人按了板子上的实体键** | `request_id='BTN-…'`、`button='MENU'` |

## 页面功能

### 第1周（展示）

- 三轴加速度实时数值卡片（单位 g，已标定：静止合加速度 ≈ 1.00g）
- 角速度三轴为 0：**板载 IMU 为 QMA6100P，仅加速度计，无陀螺仪**（硬件限制，见观测记录说明）
- 最近 60 条趋势曲线（三轴加速度，原生 canvas，无外部依赖）
- 数据年龄与「未更新」提示（超 5 秒判定过期）
- 芯片温度 / 堆内存（剩余·已用·共，MB）/ WiFi 信号强度
- 最近 8 条服务端原始记录表格（含服务器时间、来源 IP、触发方式）
- 历史数据 CSV 导出（可选范围：条数 / 最近几小时）

### 第2周（主动交互）

- **「重新采集」按钮**：向设备下发指令，让板子**现在**采一批新数据
- **四阶段时间线**：服务器受理 → 指令下发 → 设备接收 → 执行完成，每步显示到达时刻与阶段耗时；
  超时会标红并注明卡在哪一段（`accept` 设备没取走 / `exec` 未执行完）
- **用数字区分「刷新」与「重新采集」**：面板显示「下发前库里 N 条 → 下发后 M 条」，
  刷新页面这两个数不变，下发指令才会增加
- **表格标出「触发」列**：`定时` / `指令`（指令行高亮，悬浮显示 `request_id`）

### 第3周（实体交互 + 本地反馈）

- **「实体交互」面板**：显示板子上按键被按过的记录 —— 哪个键、几秒前、新采了几条、
  记录 id 区间、入库跨度、**按下→首条采样的延迟**
- **表格第三类标记**：`按键 MENU`，与「定时」「指令」用不同底色区分
- **跨度异常自动标红**：一次按键本该在几秒内传完，跨度超过 30 秒会提示
  「事件 id 可能撞车」—— 这个判断来自真实踩过的坑，见 `docs/design/09` 第 3 节
- **板端本地反馈**：按任意键绿灯短亮一下（按到了）；整批上传成功连闪 2 次；
  有失败则快闪 5 次。上电时连闪 3 次作自检

设计细节见 [`../docs/design/09-实体按键与本地反馈.md`](../docs/design/09-实体按键与本地反馈.md)，
真机证据见 [`第3周验收记录.md`](第3周验收记录.md)。

## 摄像头实时画面（附加：这块板的老本行）

### 取流方式：走服务器中转（默认）

网页默认访问 **服务器** 的 `/api/camera`，不再直连板子。链路是：

```
OV2640 → ESP32-S3-EYE (81 端口 /stream)
              ↓  只有 1 路
      server.py 的 MJPEG 中继 (camera_relay.py)
              ↓  分发
        任意多个浏览器 /api/camera
```

**为什么必须中转，不能让网页直连板子**：

| | 直连（旧） | 服务器中转（现在） |
|---|---|---|
| 板端连接数 | 每个网页各占一路 | **恒定 1 路** |
| 多人同时看 | 2 路就崩到 0.1 fps | 实测 3 个页面各有 3.5 fps |
| 网页需要知道板子 IP | 需要（且换了要改代码） | **不需要**，服务器从上报记录里自动取 |
| 以后做远程访问 | 得把板子也暴露出去 | 只需映射服务器一个端口 |

- **接口**：
  | 路径 | 内容 |
  |---|---|
  | `http://127.0.0.1:8000/api/camera` | MJPEG 视频流（服务器中转） |
  | `http://127.0.0.1:8000/api/camera/status` | 中继状态：观看人数、帧龄、板子地址、错误信息 |
  | `http://<板子IP>:81/stream` | 板端原流，**仅排障用**（网页里把 `CAM_MODE` 改成 `'direct'` 可直连） |
  | `http://<板子IP>:81/capture` | 单帧 JPEG，适合定时抓拍 |
  | `http://<板子IP>:81/ping` | 板端自检心跳 |
- **为什么 MCU 也能跑视频**：OV2640 自带 JPEG 硬编码，吐出来的就是压缩后的码流，ESP32 只负责搬运转发，不做编码。
- **实测**：QVGA 320×240，单路 6~7 fps；服务器中转，慢网络的观看者会自动丢帧保最新（`maxsize=2` 的队列），不会累积延迟。
- **断流自愈**（`camera_relay.py`）：板子会因为重启、WiFi 抖动随时掐断这条 TCP。中继自带三层兜底——连接断开后按 1.6 倍退避重连（上限 6 秒）、连续 12 秒解不出帧判定为断流并主动重建、看门狗每 2 秒检查"有人看但线程死了"的情况并拉起。`/api/camera/status` 里的 `reconnects` 就是累计重连次数，用来区分"网络偶发抖动"和"板子一直在重启"。

### 一个必须用异步 handler 的血泪坑

ESP-IDF 自带的 `esp_http_server` **是单线程**的（`httpd_main.c` 里 `while(1) httpd_server(hd)`），URI handler 同步执行。MJPEG 推流 handler 天然是永不返回的死循环，直接写在里面的后果极具迷惑性：

> 第一个人打开网页正常 → 他刷新一次或开了第二个标签页 → 旧连接还占着唯一线程 → **从此 81 端口对所有人都无响应** → 只有拔电源才恢复。

解法是 `httpd_req_async_handler_begin()`：handler 拿到请求副本立刻返回，推流交给独立任务，主线程回到 select 循环。详见 `camera_stream.c` 顶部注释。

### 摄像头功能的三个硬性前提（踩过的坑）

1. **必须开 PSRAM**（`CONFIG_SPIRAM=y`）：一帧 320×240 就是 150KB，内部 DRAM 只有 200 多 KB，**不开必崩**。开了之后日志会显示 `Found 8MB PSRAM device`，帧缓冲自动落到外部 RAM（`Allocating 15360 Byte frame buffer in PSRAM`）。
2. **SCCB 必须用旧 I2C 驱动**（`CONFIG_SCCB_HARDWARE_I2C_DRIVER_LEGACY=y`）：IDF 5.x 里新旧 I2C 驱动只要同时被链进可执行程序，**启动时直接 abort**（`CONFLICT! driver_ng is not allowed to be used with this old driver`）——这是链接期检查，跟你实际用没用无关。
3. **摄像头必须复用 IMU 那条总线**：config 里填 `.pin_sccb_sda = -1` + `.sccb_i2c_port = I2C_NUM_0`。如果填具体引脚号，它会自己再装一套 I2C 驱动抢 GPIO4/5，结果就是**摄像头起来了、IMU 反而读不到数据**。两个设备同挂一条总线（IMU=0x12，OV2640=0x30）互不影响。

## 验收演练（老师要看的）

**第 1 周 —— 数据是真的**

1. 打开页面 → 数值实时刷新，板子静置时 |a|≈1.00g

| 想证明的事 | 怎么看 |

8. **数据自带触发来源**（第2、3周）：`trigger` 三态 + `request_id` + `button`，让"这批数据是这次动作新采的"成为**数据层可直接查的字段**
9. **实体按键走 ADC 电阻梯**（第3周）：四个用户键只占一个引脚（GPIO1），固件按电压判读并做消抖 + 边沿触发；实测电压与原理图设计值偏差 ≤20 mV
10. **本地反馈用灯效序列**（第3周）：本板没有蜂鸣器也没有 RGB 灯，唯一可控的是 GPIO3 绿灯且**必须开漏驱动**；用灯效队列把"按到了/服务器收到了/没送出去"区分开
11. **观测工具自身会改变被测对象**：串口工具默认拉高 DTR/RTS 会把 ESP32-S3 复位，导致 200 秒采集空白 —— 已修复并写成案例（`docs/design/09` 第 4 节）

## 型号勘误：原理图写 QMA7981，实装是 QMA6100P

调试过程中发现原理图/手册标注的型号与实际物料不符，本组通过芯片自检确认了真实型号。这是本项目**所有寄存器级异常的根源**，也是一份完整的排错记录。

| 判据                            | 本板实测              | QMA6100P                       | QMA7981（公开手册） |
| ----------------------------- | ----------------- | ------------------------------ | ------------- |
| CHIP_ID (0x00)                | **0x90**          | 0x90 ✓                         | 0xE7 ✗        |
| 0x45 CHIP_STATE / 0x46 ULPS   | ACK（0xc0 / 0x1a）  | 有此寄存器 ✓                        | 无 ✗           |
| 0x33 NVM / 0x4A / 0x56 / 0x5F | 全部 ACK            | 有 ✓                            | 无 ✗           |
| ±2g 量程码                       | 0b0001 生效，0x00 非法 | 0b0001 ✓                       | 对不上 ✗         |
| 量程档位                          | ±2/4/8/16/32g 全接受 | 位编码 0x01/0x02/0x04/0x08/0x0F ✓ | 老手册无 ±32g ✗   |
| 软复位寄存器                        | 0x36 写 0xB6 有效    | 0x36 = SW_RESET ✓              | 无 ✗           |

**原因**：QMA7981 已 EOL 停产，QMA6100P 是其 pin-to-pin 兼容换代型号（同封装 LGA-12、同 I²C 地址 0x12、同 14 位 ADC），乐鑫后续批次换料后原理图文案未同步，但 esp-bsp 组件库已改为 `qma6100p`。

**复现方法**：固件上电自动运行 `imu_identify()`，串口打印 CHIP_ID、6 个 QMA6100P 特有寄存器探测结果、5 档量程接受性测试，结束后自动恢复 ±2g。换任何一块板都能用它自证型号。

**该发现解释的历史异常**：按 QMA7981 手册写量程 0x00 → 不生效、模长 1.5g；按旧格式套数据 → 三轴对不上；Y 轴上电冻结需软复位 → 0x36 正是 QMA6100P 的 SW_RESET。没有一个是玄学。

## 常见坑

- **Windows 防火墙拦了**：本机浏览器先访问 `http://10.1.41.18:8000` 验证，不通就给 Python 放行
- **时间对不上**：板子没有 RTC，`ts` 是上电毫秒数；权威时间是服务端的 `server_ms`
- **5GHz WiFi 连不上**：ESP32 只支持 2.4GHz
- **USB 串口只用于看日志调试**，不能算"开发板独立联网上传"（本项目走 WiFi，合规）
- **设备生成的事件 id 必须跨重启唯一**：用内存计数器的话，板子一重启就归零，
  两次不同时间的按键会生成同一个 id、被服务器误合并成一条
  （表现为"样本 10 条、跨度 105 秒"）。已改用上电随机前缀 `BTN-<6位hex>-…`。
  **这类问题产出的是"看起来对的错误证据"，比没有数据更危险**
- **串口工具别默认拉高 DTR/RTS**：ESP32-S3 上这会触发芯片复位，
  芯片一重启 USB 就重新枚举，Windows 下旧句柄**静默失效**（不报错，只是再也读不到数据）。
  打开串口后显式 `setDTR(False)` / `setRTS(False)`，并加看门狗重连
- **按键阵列是 ADC 不是 GPIO**：想加按键先看原理图，别默认每个键各占一个引脚
