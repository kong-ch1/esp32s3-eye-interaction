## 一之二、第 2 周新增：让网页能反过来指挥设备

第 1 周的链路是**单向**的：板子推数据，网页看数据。网页刷新再多次也只能看到已有记录 ——
**没有任何办法让设备再采一次**。

第 2 周补上反方向的通道，并把它做成一条可核查的证据链：

```
网页点「重新采集」
   │  POST /api/command
   ▼
① issued      服务器受理，生成 request_id 并入队
   │  板子下次上报（≤1s）时，指令随 /api/data 的**响应体**捎带下发
   ▼
② delivered   指令已到达板子
   │  板子回报 cmd_state="received"
   ▼
③ received    设备确认接收，开始按参数采集
   │  板子采完最后一条，回报 cmd_state="done"
   ▼
④ done        执行完成，新数据已入库（可按 request_id 精确回溯）
   └─ 任一步超时 → timeout，并记录卡在哪一段（accept / exec）
```

**数据层如何区分「新采集」与「历史记录」**（不靠时间窗口猜）：

| 字段 | 定时上报 | 指令触发 |
|---|---|---|
| `trigger` | `'timer'` | `'command'` |
| `request_id` | `NULL` | 该次指令的 id |

指令**不推送给设备**，而是搭车在板子自己的上报响应里 —— 板子不需要开监听端口，
也不用引入 MQTT/WebSocket，改动最小。代价是指令送达最多延迟 1 秒（等下一次上报），
对本场景完全够用；若将来要做秒级以下的实时控制，才值得换成长连接。

设计细节见 [`docs/design/08-下行指令与回执状态机.md`](docs/design/08-下行指令与回执状态机.md)，
真机验收证据见 [`week1/第2周验收记录.md`](week1/第2周验收记录.md)。

## 三、系统架构

```
┌──────────────────────────┐         ┌──────────────────────────┐        ┌─────────────────┐
│   ESP32-S3-EYE           │  WiFi   │   服务器 (server.py)      │  HTTP  │   网页           │
│                          │ 2.4GHz  │   0.0.0.0:8000           │        │  index.html     │
│  QMA6100P ──I2C──┐       │ ──────► │                          │ ◄───── │                 │
│                 ├─► app  │  POST   │  /api/data   接收存储     │  GET   │  实时数值卡片    │
│  OV2640 ──DVP───┘  main  │ /api/data│ /api/latest  最新+年龄    │        │  趋势曲线        │
│                          │         │ /api/history 历史         │        │  摄像头画面      │
│  上报周期 1Hz            │         │ /api/export.csv 导出      │        │  CSV 下载        │
│                          │         │ /api/devices 设备列表     │        │  未更新提示      │
│                          │  :81    │ /api/camera   MJPEG 中继  │        │                 │
│  MJPEG 流服务 ◄──────────┼─────────┤  (camera_relay.py)       │        │                 │
└──────────────────────────┘  拉 1 路  └───────────┬──────────────┘        └─────────────────┘
                                                   │
                                            SQLite readings.db
```

设计要点：

- **板子只推 1 路数据**，摄像头流由服务器作为「唯一客户端」拉取后分发给任意多个浏览器 —— 板端连接数恒定，多人同时观看不崩。
- **权威时间是服务端的 `server_ms`**，板子无 RTC，`device_ms` 只能用于测间隔。
- **每条记录带 `src_ip`**，这是「数据来自真实设备而非页面常量」的证据。
- 服务端**零第三方依赖**，只用 Python 标准库，换台电脑拷过去就能跑。

# 1) 启动服务器（监听 0.0.0.0:8000）

## 六、验收演练（老师要看的）

1. 打开页面 → 数值实时刷新，板子静置时 |a| ≈ 1.00 g
2. 拿起开发板晃动/翻转 → 数值与曲线同步变化
3. **拔掉板子 USB 供电** → 数值冻结、时间停在最后一刻
4. 等 5 秒 → 页面提示「未更新 · 已 N 秒」

第 3~4 步是核心：证明页面数值不是写死的，而是真的来自一台会停掉的设备。

## 八、本组相对通用示例的关键改动

1. **QMA6100P 裸驱动**：按数据手册自行实现 I2C 读写与 14 位补码数据组装，未依赖官方 BSP 组件
2. **型号勘误**：原理图标 QMA7981，实装为 QMA6100P（已通过 CHIP_ID=0x90 与 6 个特有寄存器自检确认），固件上电自动打印证据
3. **摄像头异步 handler 改造**：绕开 ESP-IDF 单线程 httpd 被 MJPEG 死循环堵死的致命问题
4. **摄像头服务器中转**：板端连接数从 N 降到 1，支持多人同时观看，并带三层断流自愈
5. **固定频率上报 + 服务端 stale 判定**：页面可证明「数据停了」
6. **服务端零依赖 + 幂等列迁移 + 容量上限自动裁剪 + CSV 范围导出**
7. **静态噪声基线分析**：用实测数据回答「板子没动为什么数值还在跳」

详细过程与踩坑记录见 [`docs/design/07-排错记录.md`](docs/design/07-排错记录.md)。

## 九、关于本仓库的提交历史

**这一点需要说明清楚：本仓库的 Git 历史是开发完成后回溯重建的，不是开发过程中实时提交的。**

开发期间本项目**没有使用 Git**。为了让考核能看到完整的开发过程，我们在学期末用开发过程中留下的三类原始记录重建了提交历史：

| 重建依据 | 内容 |
|---|---|
| 工具会话记录 | 每一次改动的**精确时间戳**（精确到毫秒）与**涉及文件清单** |
| 文件变更快照 | 每个文件在当时**是什么内容**（全文快照，非推测） |
| 每日工作日志 | 当天做了什么、为什么这么做、踩了哪些坑 |

重建结果的可验证性：

- 每个提交的**时间**取自真实记录的毫秒时间戳，不是编造的日期
- 每个提交里文件的**内容**是对该文件当时快照的还原；重建完成后，整个工作树与开发结束时的实际文件做过**逐字节比对，249 个文件全部一致**（本节文字与第九节是在该次校验之后补充的）
- 提交信息中的技术结论均可追溯到 [`docs/design/`](docs/design/) 与 [`docs/ai-conversations/`](docs/ai-conversations/) 中的对应记录

因此这份历史**如实地反映了工作的先后顺序与内容演化**，但**提交时间点本身是事后对齐的**，不代表当时执行过 `git commit`。

有两处改动在记录中没有留下变更痕迹，是按当日工作日志定位后补入对应提交的：`week1/观测记录.md` 的型号勘误同步（9-10）、`week1/firmware/esp32_imu/main/CMakeLists.txt` 加入 `camera_stream.c`（9-11）。
