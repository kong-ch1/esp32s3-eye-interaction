硬件平台：**ESP32-S3-EYE**（ESP32-S3-WROOM-1 / 8MB PSRAM / 8MB Flash / OV2640 摄像头 / QMA6100P 加速度计）

## 一、单元目标与进度

单元1 的目标是搭出一个**最小交互闭环**：单源采集 → 传输 → Web 展示，并且 Web 能反过来向设备发出请求、追踪设备是否真的执行了。

| 周次 | 内容 | 状态 |
|---|---|---|
| 第 1 周 | 单源传感采集 + 独立联网上传 + Web 实时展示与「未更新」验证 | ✅ 完成，真机链路跑通 |
| 第 2 周 | Web → 服务器 → 板子 的「重新采集」指令通道 + 回执状态机 | ✅ 完成，真机 + 真实浏览器验证通过 |
| 第 3 周 | 板载实体按键触发采集 + 本地（LED）/远端（Web）反馈闭环 | ✅ 完成，真机 + 真实浏览器验证通过 |
| 服务部署 | 用这台电脑代替 VPS（课程允许），服务跨主机可用 | ✅ 局域网内已跑通；**外出远程访问待补**（需公网/内网穿透） |

## 二、第 2 周：让网页能反过来指挥设备

第 1 周的链路是**单向**的：板子推数据，网页看数据。网页刷新再多次也只能看到已有记录 ——
**没有任何办法让设备再采一次**。

第 2 周补上反方向的通道，并把它做成一条可核查的证据链：

```
网页点「重新采集」
   │  POST /api/command
   ▼
① issued      服务器受理，生成 request_id 并入队
   │  板子下次上报（≤1s）时，指令随 /api/data 的**响应体**捎带下发
   ▼
② delivered   指令已到达板子
   │  板子回报 cmd_state="received"
   ▼
③ received    设备确认接收，开始按参数采集
   │  板子采完最后一条，回报 cmd_state="done"
   ▼
④ done        执行完成，新数据已入库（可按 request_id 精确回溯）
   └─ 任一步超时 → timeout，并记录卡在哪一段（accept / exec）
```

**数据层如何区分「新采集」与「历史记录」**（不靠时间窗口猜）：

| 字段 | 定时上报 | 指令触发 |
|---|---|---|
| `trigger` | `'timer'` | `'command'` |
| `request_id` | `NULL` | 该次指令的 id |

指令**不推送给设备**，而是搭车在板子自己的上报响应里 —— 板子不需要开监听端口，
也不用引入 MQTT/WebSocket，改动最小。代价是指令送达最多延迟 1 秒（等下一次上报），
对本场景完全够用；若将来要做秒级以下的实时控制，才值得换成长连接。

设计细节见 [`docs/design/08-下行指令与回执状态机.md`](docs/design/08-下行指令与回执状态机.md)，
真机验收证据见 [`week1/第2周验收记录.md`](week1/第2周验收记录.md)。

## 三、第 3 周：让现场的人也能触发采集

前两周的交互**都发生在远端**：板子按时上报，网页能反过来指挥设备。但站在设备旁边的
那个人没有办法和它交互 —— 他只能等，或者掏出手机打开网页。

第 3 周补上这一半：**直接按板子上的键**就能触发一次采集，并且立刻得到反馈。

```
按下实体键
   ├─► 绿灯短亮 60 ms            ← 本地反馈：按到了
   ├─► 板子采 5 条并上传          ← trigger='button'，带按键名与事件 id
   └─► 网页「实体交互」面板出现    ← 远端反馈：服务器收到了
```

### 硬件事实（查过原理图与官方文档，不是猜的）

| 项目 | 事实 | 出处 |
|---|---|---|
| 4 个用户按键 | 挂在**同一条 ADC**（`ADC1_CH0` = GPIO1）上的电阻梯，靠电压区分 | 原理图第 4 页 |
| 各键电压 | UP+ 380 / DN− 820 / PLAY 1980 / MENU 2410 mV | 原理图（实测偏差 ≤20 mV） |
| 本地反馈 | 只有一颗绿灯（GPIO3），且**必须开漏驱动、不得上拉** | 官方用户指南 |
| 蜂鸣器 / RGB 灯 | **都没有** | 原理图 + 官方 BSP 能力表 |

### 三种触发方式在数据层分得开

| 触发方式 | `trigger` | `request_id` | `button` |
|---|---|---|---|
| 定时上报 | `timer` | `NULL` | `NULL` |
| 网页下发指令 | `command` | `CMD-20260920-0002` | `NULL` |
| **板载实体按键** | `button` | `BTN-2a3613-MENU-0003` | `MENU` |

真机实测（四个键各按一次，每次恰好新采 5 条）：

| 事件 id | 按键 | 记录 id | 入库跨度 | 按下→首条采样 |
|---|---|---|---|---|
| `BTN-2a3613-UP+-0001` | UP+ | 26153 ~ 26157 | 1608 ms | 471 ms |
| `BTN-2a3613-DN--0002` | DN− | 26160 ~ 26164 | 1115 ms | 1221 ms |
| `BTN-2a3613-MENU-0003` | MENU | 26167 ~ 26171 | 968 ms | 1061 ms |
| `BTN-2a3613-PLAY-0004` | PLAY | 26175 ~ 26179 | 893 ms | 691 ms |

### 这一周也修掉了一个会产出"错误证据"的 bug

事件 id 原先是内存里的计数器，**板子一重启就归零**，于是两次不同时间按的 UP+
生成了同一个 id，被服务器按 id 聚合时**误合并成一条**（样本数 10、跨度 105 秒）。
它产出的不是"没有数据"，而是看起来像证据、实际是错的数字 —— **错的证据比没有证据更危险**。
修复方式是给事件 id 加**上电随机前缀**（`BTN-2a3613-…`），并在网页上把跨度异常的事件
直接标红提示。完整过程见 [`docs/design/09`](docs/design/09-实体按键与本地反馈.md) 第 3 节。

设计细节见 [`docs/design/09-实体按键与本地反馈.md`](docs/design/09-实体按键与本地反馈.md)，
真机证据见 [`week1/第3周验收记录.md`](week1/第3周验收记录.md)。

## 六、系统架构

```
┌──────────────────────────┐         ┌──────────────────────────┐        ┌─────────────────┐
│   ESP32-S3-EYE           │  WiFi   │   服务器 (server.py)      │  HTTP  │   网页           │
│                          │ 2.4GHz  │   0.0.0.0:8000           │        │  index.html     │
│  QMA6100P ──I2C──┐       │ ──────► │                          │ ◄─────►│  实时数值卡片    │
│                 ├─► app  │  POST   │  /api/data   接收存储     │ GET/   │  趋势曲线        │
│  OV2640 ──DVP───┤  main  │ /api/data│ /api/latest  最新+年龄    │ POST   │  摄像头画面      │
│  4键 ADC ─GPIO1─┤       │         │ /api/history 历史         │        │  CSV 下载        │
│  绿灯   ◄─GPIO3─┘       │ ◄───────┤ /api/buttons 实体按键事件  │        │  主动交互面板    │
│                          │ 捎带指令 │ /api/command 下发指令     │        │  实体交互面板    │
│  上行 1Hz + 按键突发      │         │ /api/export.csv /devices  │        │  未更新提示      │
│                          │  :81    │ /api/camera   MJPEG 中继  │        │                 │
│  MJPEG 流服务 ◄──────────┼─────────┤  (camera_relay.py)       │        │                 │
└──────────────────────────┘  拉 1 路  └───────────┬──────────────┘        └─────────────────┘
                                                   │
                                            SQLite readings.db
```

设计要点：

- **板子只推 1 路数据**，摄像头流由服务器作为「唯一客户端」拉取后分发给任意多个浏览器 —— 板端连接数恒定，多人同时观看不崩。
- **权威时间是服务端的 `server_ms`**，板子无 RTC，`device_ms` 只能用于测间隔。
- **每条记录带 `src_ip`**，这是「数据来自真实设备而非页面常量」的证据。
- **数据自带「谁触发的」**：`trigger` 三态（`timer`/`command`/`button`）+ `request_id` + `button`，
  所以"这批数据是这次动作新采的"是**数据库里的直接关联**，不是靠时间窗口猜。
- **只有一条下行通道**：板子不监听端口，待执行指令搭在 `/api/data` 的**响应体**里捎带下发，不引入 MQTT/WebSocket。
- 服务端**零第三方依赖**，只用 Python 标准库，换台电脑拷过去就能跑。

## 九、验收演练（老师要看的）

### 基本链路（第 1 周）

1. 打开页面 → 数值实时刷新，板子静置时 |a| ≈ 1.00 g
2. 拿起开发板晃动/翻转 → 数值与曲线同步变化
3. **拔掉板子 USB 供电** → 数值冻结、时间停在最后一刻
4. 等 5 秒 → 页面提示「未更新 · 已 N 秒」

第 3~4 步是核心：证明页面数值不是写死的，而是真的来自一台会停掉的设备。

### 远端指挥设备（第 2 周）

5. 点「重新采集」→ 四阶段时间线依次点亮（受理 → 下发 → 设备接收 → 完成）
6. 底部显示「下发前 N 条 → 下发后 M 条」，表格里带「指令」标记的行整行高亮

### 现场的人与设备交互（第 3 周）

7. **直接按板子上的 MENU / PLAY / UP+ / DN−** → 板上的绿灯**先短亮一下**（本地反馈）
8. 紧接着看网页「实体交互」面板 → 出现这次按键：哪个键、几秒前、新采了几条
9. 表格里带「按键 MENU」标记的行与「定时」行用不同底色区分

第 7 步是这一周的重点：**反馈发生在两个地方** —— 手上的灯和屏幕上的记录，
而且两者都指向同一次真实的物理操作。

## 十一、本组相对通用示例的关键改动

1. **QMA6100P 裸驱动**：按数据手册自行实现 I2C 读写与 14 位补码数据组装，未依赖官方 BSP 组件
2. **型号勘误**：原理图标 QMA7981，实装为 QMA6100P（已通过 CHIP_ID=0x90 与 6 个特有寄存器自检确认），固件上电自动打印证据
3. **摄像头异步 handler 改造**：绕开 ESP-IDF 单线程 httpd 被 MJPEG 死循环堵死的致命问题
4. **摄像头服务器中转**：板端连接数从 N 降到 1，支持多人同时观看，并带三层断流自愈
5. **固定频率上报 + 服务端 stale 判定**：页面可证明「数据停了」
6. **服务端零依赖 + 幂等列迁移 + 容量上限自动裁剪 + CSV 范围导出**
7. **静态噪声基线分析**：用实测数据回答「板子没动为什么数值还在跳」
8. **下行指令搭车上行响应**：不给板子开监听端口、不引入 MQTT/WebSocket，指令随 1Hz 上报的响应体捎带下发
9. **四阶段回执状态机**：issued → delivered → received → done，超时还分 `accept`/`exec` 两段，故障可定位
10. **数据自带触发来源**：`trigger` 三态 + `request_id` + `button`，让「这批数据是这次动作新采的」成为数据库里的直接关联
11. **实体按键走 ADC 电阻梯**：四个键只占 GPIO1；按键电压实测与原理图偏差 ≤20 mV
12. **本地反馈用灯效序列**：单色灯 + 队列化灯效任务，用闪法区分"按到了/服务器收到了/没送出去"
13. **观测工具自身会改变被测对象**：串口工具默认拉高 DTR/RTS 会把 ESP32-S3 复位，导致 200 秒采集空白 —— 已修并写成排错案例

详细过程与踩坑记录见 [`docs/design/07-排错记录.md`](docs/design/07-排错记录.md)。

## 十二、关于本仓库的提交历史

**这一点需要说明清楚：本仓库的 Git 历史是开发完成后回溯重建的，不是开发过程中实时提交的。**

开发期间本项目**没有使用 Git**。为了让考核能看到完整的开发过程，我们在学期末用开发过程中留下的三类原始记录重建了提交历史：

| 重建依据 | 内容 |
|---|---|
| 工具会话记录 | 每一次改动的**精确时间戳**（精确到毫秒）与**涉及文件清单** |
| 文件变更快照 | 每个文件在当时**是什么内容**（全文快照，非推测） |
| 每日工作日志 | 当天做了什么、为什么这么做、踩了哪些坑 |

重建结果的可验证性：

- 每个提交的**时间**取自真实记录的毫秒时间戳，不是编造的日期
- 每个提交里文件的**内容**是对该文件当时快照的还原；重建完成后，整个工作树与开发结束时的实际文件做过**逐字节比对，249 个文件全部一致**（本节与上面「分支与周次对照」一节，都是在这次逐字节校验之后才补写的）
- 提交信息中的技术结论均可追溯到 [`docs/design/`](docs/design/) 与 [`docs/ai-conversations/`](docs/ai-conversations/) 中的对应记录

因此这份历史**如实地反映了工作的先后顺序与内容演化**，但**提交时间点本身是事后对齐的**，不代表当时执行过 `git commit`。

有两处改动在记录中没有留下变更痕迹，是按当日工作日志定位后补入对应提交的：`week1/观测记录.md` 的型号勘误同步（9-10）、`week1/firmware/esp32_imu/main/CMakeLists.txt` 加入 `camera_stream.c`（9-11）。
