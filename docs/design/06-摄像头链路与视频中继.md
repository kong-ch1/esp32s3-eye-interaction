# 06 · 摄像头链路与视频中继

涉及文件：

- 板端：[`week1/firmware/esp32_imu/main/camera_stream.c`](../../week1/firmware/esp32_imu/main/camera_stream.c) / `.h`
- 服务端：[`week1/server/camera_relay.py`](../../week1/server/camera_relay.py)，由 `server.py` 挂到 `/api/camera`
- 网页：`index.html` 的摄像头区块

## 1. 为什么 MCU 也能跑视频

**OV2640 传感器自带 JPEG 硬编码** —— 它吐出来的就是压缩好的 JPEG 码流，ESP32 只负责搬运转发，**不需要自己做任何编码**。这是本方案能成立的根本原因。

实测：QVGA 320×240，单路 6~7 fps，一帧 6~7 KB。

## 2. 链路演进：从直连到服务器中转

```
【阶段一 · 直连】
  浏览器 ──── http://板子IP:81/stream ────► 板子
  浏览器 ──── http://板子IP:81/stream ────► 板子
  → 板端 N 路连接，2 路就崩到 0.1 fps

【阶段二 · 服务器中转（最终方案）】
  浏览器 ──┐
  浏览器 ──┼──► 服务器 /api/camera ──► camera_relay ──► 板子 :81/stream
  浏览器 ──┘        （分发 N 路）        （恒定 1 路上游）
```

### 对比

| | 直连 | 服务器中转 |
|---|---|---|
| 板端连接数 | 每个网页各占一路 | **恒定 1 路** |
| 多人同时看 | 2 路就崩到 0.1~0.2 fps | 实测 **3 个页面各有 3.2~3.6 fps** |
| 网页是否需要知道板子 IP | 需要（换了要改代码） | **不需要**，服务器从上报记录里自动取 |
| 远程访问 | 得把板子也暴露出去 | 只需映射服务器一个端口 |

### 相关接口

| 路径 | 内容 |
|---|---|
| `http://服务器:8000/api/camera` | MJPEG 视频流（服务器中转，网页默认用它） |
| `http://服务器:8000/api/camera/status` | 中继状态：观看人数、帧龄、板子地址、重连次数、错误信息 |
| `http://板子IP:81/stream` | 板端原流，**仅排障用**（网页把 `CAM_MODE` 改成 `'direct'` 可直连） |
| `http://板子IP:81/capture` | 单帧 JPEG，适合定时抓拍 |
| `http://板子IP:81/ping` | 板端自检心跳（uptime / clients / heap） |
| 板端 `GET /` | 板子自带预览页，用于区分「是网页问题」还是「板子问题」 |

## 3. ★ 板端最关键的一个坑：单线程 httpd

**ESP-IDF 自带的 `esp_http_server` 是单线程的**（`components/esp_http_server/src/httpd_main.c`）：

```c
while (1) { httpd_server(hd); }
```

URI handler 在这唯一的线程里**同步执行**。只要有一个 handler 不返回，整个服务器就彻底卡死 —— 新连接没人 `accept`，`/capture` 也没人应答。

而 MJPEG 推流 handler 天然就是死循环（客户端不断开就一直推帧）。直接写成同步 handler 的后果**极具迷惑性**：

> 第一个人打开网页正常 → 他刷新一次或开第二个标签页（旧的 `/stream` 连接还占着线程）
> → **从此 81 端口对所有人都无响应** → 只有重新上电才恢复。

这正是当时「有时能用、大多时候不行」的真正原因。

### 解决办法：异步 handler

```c
httpd_req_async_handler_begin()   // 拿到请求副本
→ 立即 return
→ 推流交给独立 FreeRTOS 任务（8192 栈，优先级 6，绑核 1）
→ httpd 主线程回到 select 循环
```

### 配套的防护措施

| 措施 | 目的 |
|---|---|
| 客户端名额（mutex 保护的计数，上限 2，`CAM_MAX_STREAM_CLIENTS`） | 超限返回 **503 快速失败**，而不是挂起 |
| `lru_purge_enable = true` | 防止连接泄漏 |
| `recv/send_wait_timeout = 2` | 避免长阻塞 |
| `SO_KEEPALIVE` + `TCP_KEEPIDLE=15 / KEEPINTVL=5 / KEEPCNT=3` | 及时回收死连接 |
| `TCP_NODELAY` | 关闭 Nagle，否则三次小写入被攒包导致画面卡 |
| 区分 `errno` 的抖动容忍 | `EAGAIN/EWOULDBLOCK`（对方窗口满 / WiFi 一时堵）→ 丢帧继续，**连续 8 次才认输**（`CAM_EAGAIN_TOLERANCE`）；`104 ECONNRESET` / `128 ENOTCONN` → 立即收摊 |

> 抖动容忍是第二轮补的。之前一遇超时就退出推流，导致「客户端不停重连却一直没画面」的死循环。

### 实测验证

连续 5 轮「建立 → 拉 4 秒 → 断开」，断开后 `/ping` 都能在 0.1~0.3 秒回应，`/capture` 正常返回（改造前第 2 轮必死）。

## 4. 摄像头的三个硬性前提

### 4.1 必须开 PSRAM

`CONFIG_SPIRAM=y`。一帧 320×240 就是 ~150 KB，内部 DRAM 只有 200 多 KB，**不开必崩**。
开了之后日志会显示 `Found 8MB PSRAM device`，帧缓冲自动落到外部 RAM（`Allocating 15360 Byte frame buffer in PSRAM`）。

### 4.2 SCCB 必须用旧版 I²C 驱动

`CONFIG_SCCB_HARDWARE_I2C_DRIVER_LEGACY=y`。

IDF 5.x 里新旧 I²C 驱动只要**同时被链进可执行程序**，启动时直接 abort：

```
E i2c: CONFLICT! driver_ng is not allowed to be used with this old driver
```

这是 `__attribute__((constructor))` 在链接期做的检查（`components/driver/i2c/i2c.c` 的 `check_i2c_driver_conflict()`），**跟你实际有没有用新驱动无关**。该开关让 camera 组件选 `driver/sccb.c` 而非 `sccb-ng.c`。（另有 `CONFIG_I2C_SKIP_LEGACY_CONFLICT_CHECK` 可关掉检查。）

### 4.3 摄像头必须复用 IMU 那条总线

```c
.pin_sccb_sda  = -1,
.sccb_i2c_port = I2C_NUM_0,
```

如果填具体引脚号，esp32-camera 会自己再装一套旧版 I²C 驱动去抢 GPIO4/5，结果是**摄像头起来了、IMU 反而读不到数据**（GPIO 输出矩阵被后装的抢走）。两个设备同挂一条总线（IMU=`0x12`，OV2640=`0x30`）互不影响。

## 5. 服务端中继：三层断流自愈

板子会因为重启、WiFi 抖动随时掐断这条 TCP。中继自带三层兜底：

| 层 | 机制 |
|---|---|
| ① 重连退避 | 连接断开后按 **1.6 倍**退避重连（上限 6 秒） |
| ② 卡死检测 | 流还连着但连续 **12 秒解不出帧** → 判定断流，主动重建（靠 TCP 超时可能要几十秒才报错） |
| ③ **看门狗** | 每 2 秒检查「还有订阅者但 pump 线程不在」→ 拉起 |

### ★ 修过的根因 bug

`_run()` 原来是**一次性**的：上游一断（板子重启 / WiFi 抖动掐断 TCP）线程就退出并置 `error`。而重启 pump 的路径只有 `subscribe()` —— **如果断流那一刻恰好没有观看者，就再也没有人调用 `subscribe`，中继会永远停在 error 对外 503**，表现为「摄像头彻底坏了、刷新也没用」。

实测当时的状态：`state=error, upstream_running=False, last_frame_age=69秒, error='读取中断: timed out'`，而板子活着（IMU 1.2 秒前还在上报，ping 0% 丢失）。

**修复**：`_run()` 改成外层重连环（`_connect_and_stream()` 返回结束原因，非 `"no_viewers"` 就退避重连）+ 新增看门狗线程 —— **看门狗是根治的那一条**。

### 其他设计细节

- **上游按需拉起**：没人观看超过 5 秒自动断开上游，省板子资源。
- **下游队列 `maxsize=2`**：满了丢旧帧保最新，**慢网络的观看者不会累积延迟**。
- **上游断开时向所有订阅者投哨兵 `None`**，让 `<img>` 触发 `onerror` → 页面自动重连。
- **板子 IP 由注入回调获取**（`CameraRelay(latest_ip_fn=...)`，从 `readings.src_ip` 最新一条取），换路由器导致 IP 变了不用改代码；也可 `--camera-url` 写死。
- `/api/camera` 首帧等待从 8 秒放宽到 **15 秒** —— 板子重启后要先连 WiFi 再起摄像头，8 秒不够会导致「重连→没帧→再重连」的循环。
- `status` 新增 `reconnects` / `state_since` 字段，便于区分「偶发抖动」和「板子在反复重启」。

### 实测

- 第 1 轮 13.6s / 26 帧 ≈ 1.92 fps；断开 8 秒后自动 idle；**第 2 轮无需重启服务器直接恢复到 2.56 fps**
- 板子 25 秒内 `seq` 无回跳（没重启），但上报间隔偶尔到 5~7 秒 → 这解释了网页偶发的「未更新」，是 WiFi 被视频流挤占所致

## 6. 排查技巧：「到底是板子死了还是中转死了」三连

比直接刷网页快得多：

1. `ping 板子` —— 网络通不通
2. `/api/latest` 看 `age` —— 板子还在不在上报
3. `/api/camera/status` 看 `state` / `upstream_running` —— 中继活着没
