## ⚠️ 0. 安全边界（先说这个）

**本功能只连接本组教学接收端。它没有任何外呼能力** —— 不打电话、不发短信、
不推送任何第三方服务。按键唯一的动作是往本组服务器写一条记录、并在本站网页上显示出来。

这条边界不是写在文档里就算数，它落在三个地方：

| 位置 | 落实方式 |
|---|---|
| 代码 | 固件里只有 `SERVER_BASE` 一个网络出口；工程中不存在任何拨号/短信/推送能力 |
| 接口 | 所有求助相关响应都带 `safety` 字段，由服务器统一注入，避免漏掉某一处 |
| 界面 | 面板顶部常驻橙色警示条：**不会连接或拨打任何真实紧急服务**，并给出 110 / 120 |

## 1. 一次按键产生两样东西

任务卡说按键要"发起**教学求助测试消息**"，不是"采一批数据"。所以按键的产物拆成两件：

| 产物 | 去向 | 生命周期 |
|---|---|---|
| **① 求助事件**（主件） | `help_events` 表 | 有状态：待回应 → 已回应 → 已取消；要被人操作 |
| **② 环境快照**（上下文） | `readings` 表（`trigger='button'`） | 写完就完了，只给回应的人一点上下文 |

**为什么求助事件单独一张表，而不是塞进 `readings`**：两者的生命周期完全不同。
塞在一起会让一半字段永远为空 —— 第2周把实体按键硬塞进指令表时已经吃过一次这个亏
（实体按键没有下行通道，压根不存在"服务器受理""指令下发"两段）。

两件产物共用同一个 `event_id`（形如 `BTN-<6位hex>-<KEY>-NNNN`），所以可以精确对上。
那个随机前缀是第3周踩坑的结果：只用内存计数器的话，板子重启后计数器归零，
两次不同时间按的键会生成同一个 id —— 见 [`09-实体按键与本地反馈.md`](09-实体按键与本地反馈.md)。

## 2. 简要流程（任务卡要求"绘制简要流程并明确取消"）

```
   站在板子旁边的人                网络                远端看网页的人
   ─────────────────               ────               ──────────────

   ① 按下 MENU / PLAY / UP+ / DN-
        │
        │  板端立刻亮灯（短亮一下）        ← ① 本地确认：不经过网络，断网也有效
        │
        └──► POST /api/help ──────────► 服务器落库
             （含环境快照 + local_feedback="led"）
                                              │
                    ┌─────────────────────────┘
                    │  ② VPS 接收：证据 = 服务器时间戳 created_ms
                    ▼
             网页「教学求助」面板出现这一条
             状态 = 待回应（open）
                    │
                    ├───────────────► ③ 查看者回应
                    │                  真人点「我来处理」→ 记录 ack_ms + ack_by
                    │                  ★ 只有这一步真的发生，界面才显示"已回应"
                    │
                    └───────────────► ④ 取消
                                       真人点「取消求助」→ 记录 cancel_ms + 原因
                                       ★ 取消是**显式动作**，不是"超时自动消失"

        ┌─────────────── 回应/取消都要回到设备（迁移确认/取消机制）───────────────┐
        │  服务器生成 help_reply 指令（含 event_id + action）                      │
        │  → 搭车在板子下一次上报/心跳的**响应体**里下发                            │
        │  → 板子取走后：ack 慢闪 4 次 / cancel 长亮 1 秒                           │
        │  → 板子回复执 received → done，证明"站在设备旁边的人确实收到了"            │
        └──────────────────────────────────────────────────────────────────────┘
```

**取消为什么要显式**：如果求助只能"自然消失"（超时、刷新、没人管），
那么发起者永远无法判断"是没人看见，还是已经处理完了"。
取消是一个明确的操作，且**留有操作人和原因**，三件事因此在数据层可分：
待回应 / 已回应 / 已取消。

## 3. 三级反馈：三件独立的事，各有各的证据

任务卡要求讲解"本地确认、VPS接收和查看者回应的区别"。它们的区别就是**证据来源不同**：

| 级别 | 发生在哪 | 证据是什么 | 断网时 |
|---|---|---|---|
| ① **本地确认** | 设备上（灯） | **设备自报** `local_feedback="led"` —— 这是设备的话，不是服务器的观测 | **仍然成立** |
| ② **VPS 接收** | 服务器 | 服务器落库时刻 `created_ms`（服务器时钟） | 不成立 |
| ③ **查看者回应** | 网页上（真人点击） | `ack_ms` + `ack_by` | 不成立 |

接口不把三级合并成一个"状态"，而是**显式拆成三个字段**分别给出，
并且每一级都把"证据是什么"一起返回：

```json
"levels": {
  "local":  {"done": true,  "how": "led", "evidence": "设备自报（不是服务器观测）",
             "note": "板端已给出物理反馈，断网也有效"},
  "server": {"done": true,  "at": "2026-09-23 11:14:06.351",
             "evidence": "服务器落库时刻（服务器时钟）", "note": "VPS 已接收这条求助"},
  "viewer": {"done": false, "at": null, "by": null,
             "evidence": "网页上真人点击「我来处理」",
             "note": "还没有人回应 —— 因此界面不显示「对方已收到」"}
}
```

### 那条硬规矩怎么落到代码里

> **无远端接收证据时不得显示"对方已收到"。**

不靠自觉，靠结构：

- `levels.viewer.done` 的唯一来源是数据库里的 `ack_ms`。没有人点过按钮，这个字段就是假。
- 界面上的 ③ 徽标直接绑 `done`，**没有别的判断路径**。
- ① 的说明里明确写着证据是"设备自报"，不冒充服务器观测。
- 三级用三种颜色分开显示，**绝不合并成一句话** —— 合并正是这条规矩最容易被违反的方式：
  一句"已处理"就把"灯亮了"和"有人回应了"混成同一件事。

## 4. 状态机与幂等

```
        POST /api/help
              │
              ▼
        ┌──────────┐   ack    ┌────────────────┐
        │   open   │ ───────► │ acknowledged   │
        │ 待回应    │          │ 已回应          │
        └────┬─────┘          └───────┬────────┘
             │                        │
             │        cancel          │  cancel
             └───────────┬────────────┘
                         ▼
                 ┌───────────────┐
                 │  cancelled    │  ✔ 终态
                 └───────────────┘
```

| 规则 | 理由 |
|---|---|
| `cancelled` 之后不能再 `ack`（返回 409） | 终态不可逆。已经结束的事不该被改写成"有人回应过" |
| 重复 `ack` 返回 `duplicate`，不生成第二条回传指令 | 与第2周终态回执幂等同理：重复的动作不携带新信息 |
| 同 `event_id` 重复上报求助 → 不入库第二条 | 设备重试是必然的（发出去和收到回应是两件事），服务器必须对重试免疫 |
| 已回应之后仍允许取消 | 现场情况会变（人到了、问题自己好了）。允许撤回比强迫走完更贴近真实使用 |

**"没新建"不等于"没有"**：重复 `ack` 时接口仍然报出**上一次那条**回传指令的 id，
只是把 `reply_command_created` 置为 `false`。否则界面会显示"没有回传指令"，与事实相反。

## 5. 迁移"确认/取消机制"：把结果送回设备

任务卡最后一条要求把确认/取消机制**迁移**出去。本项目的做法是让它回到发起者身边：

```
网页点「我来处理」/「取消求助」
   → 服务器生成 help_reply 指令（params: {event_id, action, by}）
   → 搭车下发（板子只 POST 不监听，指令塞在它上报请求的响应体里）
   → 板子 dispatch_command() 识别 help_reply → 播对应灯效
   → 板子延后回复回执 received → done
```

**为什么要回复执**：回执证明的不是"设备执行了什么资源操作"，而是
**"站在设备旁边的人确实收到了『有人回应』这件事"** —— 这正是闭环缺的最后一段。
有了 `done`，这条链路才算真的闭上，而不是网页上单方面宣布"已通知设备"。

### 灯效对照表（本地反馈的全部语义）

本板**没有蜂鸣器**、也没有可编程 RGB 灯，唯一软件可控的发光器件是绿色状态灯（GPIO3），
必须开漏驱动（见 [`09-实体按键与本地反馈.md`](09-实体按键与本地反馈.md)）。所以灯效必须省着用、且互相好区分：

| 灯效 | 含义 | 谁触发 | 属于哪一级反馈 |
|---|---|---|---|
| 开机连闪 3 次 | 自检（确认灯是活的、极性对） | 上电 | — |
| **短亮一下（60ms）** | 按到了 | 按下瞬间 | **① 本地确认** |
| **连闪 2 次（120ms）** | 服务器收到了 | 求助消息送达 | **② VPS 接收** |
| **慢闪 4 次（350ms）** | 有人回应了 | 收到 `help_reply: ack` | **③ 查看者回应** |
| **长亮 1 秒** | 求助已取消 | 收到 `help_reply: cancel` | 取消 |
| 快闪 5 次（60ms） | 没送出去 | 求助消息发送失败 | — |

本地确认刻意"快而短"，远端反馈刻意"慢而长" —— 站在板子旁边的人在余光里也能分清
"是我按到了"还是"有人回我了"。两者长得像的话，这个反馈就等于没有。

## 6. 板子侧：按键语义的变化

第3周最初把按键做成"采 5 条数据"。按任务卡原文，语义应该是**发起教学求助测试消息**，
数据只是它的上下文。改动：

| | 改前 | 改后 |
|---|---|---|
| 按键的主产物 | 5 条 IMU 采样 | **1 条求助事件**（含环境快照） |
| 上下文采样 | 就是主产物本身 | **2 条**，纯 best-effort |
| 灯效含义 | 只反映"采样是否送达" | 反映求助消息是否送达；回应/取消另有灯效 |
| 上报接口 | `/api/data` | `/api/help` + `/api/data`（两者共用同一个 `event_id`） |

**为什么上下文采样只有 2 条**：实测一次 HTTP 往返要 0.5~2.5 秒（见
[`第2周验收记录.md`](../../week1/第2周验收记录.md) 遗留一节），采样越多，
站在板子旁边的人等得越久 —— 与"按下就该立刻有反馈"直接冲突。

**上下文采样失败不影响求助的成败判定**：把"上下文没传全"当成"求助失败"，
会让灯效给出错误的坏消息（快闪 5 次），让旁边的人以为没人能收到他的求助。

而 `run_command()`（指令触发的采集）里恰好相反：**读不到传感器就如实回报 failed**。
两处的价值排序不同 —— 求助的价值在"把消息送出去"，采集的价值在"数据本身"。

## 7. 已知限制

1. **求助依赖网络**：断网时本地确认成立（灯会亮），但服务器和网页都不会有记录。
   目前**没有离线补发** —— 这是刻意的：一条几分钟后才到的求助会给回应者错误的紧迫感。
   代价是断网期间的求助会永久丢失，界面上通过灯效（只短亮、不连闪 2 次）暴露出来。
2. **只有一个待发回执槽位**：若两条控制指令在回执发完前接连到达，前一条的回执会被覆盖、
   最终走到 `exec` 超时。这是**可见**的失败（指令列表里看得到），不是静默丢数据。
3. **DHCP 依赖**：板子靠 DHCP 取地址。若路由器/热点的 DHCP 异常，
   旧固件会**永久卡在等待 IP**；现已改为每 15 秒主动重连一次并打印原因（见第 8 节）。
4. **无鉴权**：任何能访问该端口的人都能回应/取消任何求助。教学环境下可接受，
   公网暴露前必须加 token 与身份。
5. **回应人身份靠自觉填写**：第三级反馈的"真人"证据是"有人从网页点了按钮并留下名字"，
   系统不校验这个人的身份。要真正防冒名需要接入身份认证。
6. **只有一个本地输出**：本板无蜂鸣器、无 RGB，所有反馈都要挤在一颗绿灯上。
   灯效数量已经偏多，再加语义会很勉强。

## 8. 本次实测发现的三个环境/工具问题（不是代码 bug，但会误导排查）

1. **串口工具会把板子弄下线**。本板 COM5 是 ESP32-S3 **自带的 USB-Serial/JTAG**
   （不是独立 USB 转串口芯片），打开/关闭端口会直接影响芯片的复位状态。
   2026-09-23 实测：串口探针的无限重连跑到第 10 次时，板子彻底静默、
   网络上报也一起停了（服务器侧 82 秒没有任何新记录），最后靠重新烧录才恢复。
   → 已修：`tools/btn_probe.py` 的重连次数**封顶 2 次**，并在超限时明确提示
   "这更可能是观测工具在打扰被测对象"。**结论：串口采集与真机验收不要同时做。**
2. **`esptool` 的 RTS 硬复位在 USB-Serial/JTAG 模式下不一定生效**，
   可用 `--after watchdog_reset` 代替。
3. **API 返回值的命名要一致**。求助接口的 POST 曾返回 `reply_command_id`、
   GET 却返回 `reply_cmd_id`（数据库列名），同一个东西两个名字。
   → 已统一为 `reply_command_id`，并在 `to_public()` 里把原始列名弹掉，
   避免"同一份数据两个名字"这种迟早会踩的坑。
