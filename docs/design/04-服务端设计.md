# 04 · 服务端设计

实现文件：[`week1/server/server.py`](../../week1/server/server.py) + [`week1/server/camera_relay.py`](../../week1/server/camera_relay.py)

## 1. 设计约束

| 约束 | 决策 |
|---|---|
| 课程环境机器不可控（机房 PC / 借来的笔记本） | **零第三方依赖**，只用 Python 标准库 |
| 板子 1 秒 1 条，长时间挂机 | 必须**自动裁剪**，不能把磁盘写满 |
| 要用数据做分析 | 提供 **CSV 导出**，支持范围筛选 |
| 板子无 RTC | 时间以**服务端 `server_ms`** 为准 |
| 要能证明数据来自真机 | 每条记录带 **`src_ip`** |

技术栈：`http.server.ThreadingHTTPServer` + `sqlite3`。

## 2. 数据表结构

```sql
CREATE TABLE IF NOT EXISTS readings (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT    NOT NULL,
    seq       INTEGER DEFAULT 0,
    ax REAL, ay REAL, az REAL,
    gx REAL, gy REAL, gz REAL,
    device_ms INTEGER DEFAULT 0,
    server_ms INTEGER NOT NULL,
    src_ip    TEXT
);
CREATE INDEX IF NOT EXISTS idx_readings_device ON readings(device_id, id DESC);
```

### 2.1 幂等列迁移

后续新增的板端状态字段（温度、堆内存、RSSI）通过 `ALTER TABLE ADD COLUMN` 补上，**老数据一行不丢**：

```python
EXTRA_COLUMNS = {
    "temp_c": "REAL",
    "free_heap": "INTEGER",
    "min_free_heap": "INTEGER",
    "total_heap": "INTEGER",   # 堆总大小，用于算「已用多少」
    "rssi": "INTEGER",         # WiFi 信号强度 dBm，负值，越接近 0 越好
}

def migrate(conn):
    """给已存在的老库补上新列。幂等：重复执行无副作用。"""
    cols = {r["name"] for r in conn.execute("PRAGMA table_info(readings)")}
    for name, typ in EXTRA_COLUMNS.items():
        if name not in cols:
            conn.execute("ALTER TABLE readings ADD COLUMN %s %s" % (name, typ))
    conn.commit()
```

> 注意：**改完代码必须重启服务器** 才会执行迁移。
> `CREATE TABLE IF NOT EXISTS` 对已存在的表不会补列，所以必须有这段 `migrate()`。

`fnum / fint` 两个辅助函数支持 **NULL**（老固件不报这些字段时，写入 NULL 而不是 0）—— 页面据此显示「—」而不是硬算成 0。

## 3. 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/data` | 板端上传一条记录，必填 `device_id` |
| GET | `/api/latest` | 最新一条 + `age_seconds` + `stale` |
| GET | `/api/history?limit=N` | 最近 N 条 |
| GET | `/api/devices` | 设备列表 + 各设备条数 + 累计总数 + 容量上限 |
| GET | `/api/export.csv` | CSV 导出，支持 `limit=` / `hours=` / `device_id=` |
| GET | `/api/camera` | MJPEG 视频流（服务器中转） |
| GET | `/api/camera/status` | 中继状态（观看人数、帧龄、重连次数、错误） |
| GET | `/` | 展示页面 |
| OPTIONS | `*` | CORS 预检 |

服务端额外记录两个字段作为**证据**：
- `server_ms`：服务器收到时刻（毫秒）
- `src_ip`：来源 IP —— 板子 WiFi IP 为 `10.1.41.160`，与服务器所在 PC 的 `10.1.41.18` 不同主机

## 4. 「未更新」判定

```python
STALE_SECONDS = 5.0   # 超过这个秒数没收到新数据，判定为「未更新」

# /api/latest 返回
{
  ...记录字段...,
  "age_seconds": (now - server_ms) / 1000,
  "stale": age_seconds > STALE_SECONDS
}
```

可通过命令行 `--stale` 调整。

> 修过的 bug：`main()` 里原来的 `global STALE_SECONDS` 声明位置有问题，导致 `--stale` 只改了局部变量、**实际不生效**。后来把 `global MAX_ROWS, STALE_SECONDS` 提到 `main()` 第一行才修好。

## 5. 容量上限与自动裁剪

板子 1 秒 1 条，一天就是 8.6 万条，库会一直涨。

```python
MAX_ROWS = 200000          # 约 2.3 天
TRIM_CHECK_EVERY = 500     # 每插入 500 条才检查一次
TRIM_CHECK_SECONDS = 60.0  # 或每 60 秒检查一次
```

```python
def maybe_trim(conn, force=False):
    """记录数超过 MAX_ROWS 时，删掉最早的那批，把库压回上限以内。"""
    global _trim_counter, _trim_last_ts
    _trim_counter += 1
    now = time.time()
    if not force and (_trim_counter < TRIM_CHECK_EVERY
                      and now - _trim_last_ts < TRIM_CHECK_SECONDS):
        return
    ...
    total = conn.execute("SELECT COUNT(*) FROM readings").fetchone()[0]
    if total <= MAX_ROWS:
        return
    over = total - MAX_ROWS
    conn.execute(
        "DELETE FROM readings WHERE id IN"
        " (SELECT id FROM readings ORDER BY id ASC LIMIT ?)", (over,))
```

**设计要点**：

- **双向节流**（条数 + 时间），避免每来一条都 `COUNT(*)`。
- 调用点有三处：① `do_POST` 插入后（**在 `with LOCK` 内**，保证并发安全）；② `main()` 启动时 `force=True`（上次运行可能已经超了）；③ 命令行 `--max-rows` 可覆盖默认值。
- 修剪逻辑是 `ORDER BY id ASC LIMIT over` —— `id` 是自增主键，升序即最早写入的。

> ⚠️ **这是真删除、不可恢复。**
> 实测以 `--max-rows 15000` 启动，立即触发「记录 16023 条超过上限 15000，已删除最早的 1023 条」，设备列表里旧的 `team01-esp32`（551 条）被一并裁掉。
> 提醒：SQLite 删除后**文件不会自动变小**（空间被复用），要真正缩容得 `VACUUM`。

## 6. CSV 导出

### 6.1 三个刻意的设计选择

| 选择 | 原因 |
|---|---|
| **时间正序**（id 升序） | 表格看最新在前更方便，但导出拿去分析要按时间从早到晚 |
| 正文开头写 **UTF-8 BOM** | 否则 Excel 双击打开中文表头是乱码 |
| `Content-Disposition: attachment` | 触发浏览器下载，而不是在页面里内联打开 |

```python
sql += " ORDER BY id DESC LIMIT ?"      # 先取最新的 N 条
...
rows = list(reversed(rows))             # 再翻转成正序
```

### 6.2 范围筛选

| 参数 | 含义 |
|---|---|
| `limit=N` | 最多 N 条（上限 `EXPORT_LIMIT = 200000`） |
| `hours=N` | 只导出最近 N 小时（`server_ms >= (now - hours*3600)*1000`） |
| `device_id=X` | 只导出某设备 |

两者可组合，SQL 用 `WHERE 1=1` 打底便于拼接多个条件。

实测：`limit=100` → 100 行；`hours=1` → 1215 行（跨度正好 1 小时）；`hours=24` → 3768 行；`all` → 15817 行（最早到 2026-09-08）。

### 6.3 导出字段（16 列）

```
id, device_id, seq, server_time, device_ms,
ax, ay, az, gx, gy, gz,
temp_c, free_heap, min_free_heap, total_heap, src_ip
```

实测响应头：`HTTP 200`、`text/csv; charset=utf-8`、`attachment; filename="readings_20260914_163404.csv"`，BOM 正确、id 递增、中文表头正常。

## 7. 并发与线程安全

- 用 `ThreadingHTTPServer`，每个请求一个线程。
- SQLite 连接 `check_same_thread=False`，所有读写包在 `LOCK`（`threading.Lock`）内。
- **特别地，`maybe_trim()` 也必须在 `with LOCK` 内调用** —— 否则修剪与插入并发时会互相干扰。

## 8. 模块导入的一个坑

`server.py` 需要 `import camera_relay`，同目录导入必须显式补路径：

```python
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from camera_relay import CameraRelay, CLIENT_BOUNDARY, FRAME_BOUNDARY
```

**不要写成反向导入**（`camera_relay.py` 里 `from server import ...`）—— 会造成循环依赖 + `sys.path` 问题。板子 IP 改为**注入回调**：`CameraRelay(latest_ip_fn=...)`，由 `server.py` 传入一个从 `readings.src_ip` 取最新一条的函数，这样换路由器导致板子 IP 变了也不用改代码。

## 9. 启动方式

```bash
python server/server.py --port 8000             # 监听 0.0.0.0:8000
python server/server.py --stale 5 --max-rows 200000
```

Windows 上双击 `week1/start_server.bat` 可获得独立窗口。

> ⚠️ **运维坑**：用工具的后台任务方式启动 `server.py`，**任务被回收时子进程会一起被杀**，日志里**没有任何 traceback**（全是正常 200 请求记录），只有事后查 8000 端口才发现无监听。
> 判断方法：看 `debug_logs/server_runN.log` 末尾是否有 traceback —— 没有 = 被外部终止，不是代码崩。
> 长期自用请双击 `start_server.bat`（独立窗口，不受会话影响）。

## 10. 已知不足

- 没有鉴权，任何人只要在同一网段就能 POST 数据（课程内部使用，可接受）。
- 数据库无 VACUUM 定时任务，删除后空间不回收。
- 单机单进程，未做持久化队列；进程挂掉期间的数据由板子侧丢弃（板子不缓存）。
