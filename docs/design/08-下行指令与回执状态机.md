# 08 · 下行指令与回执状态机（第2周）

第 1 周搭好的是**单向**链路：板子 → 服务器 → 网页。板子是纯发布者，网页是纯旁观者 ——
**刷新页面只能看到已经存在的数据，无法让设备再采一次。**

第 2 周补上反方向的第二条通道，并把它做成一条**可核查的证据链**。

| 文件 | 职责 |
|---|---|
| [`week1/server/commands.py`](../../week1/server/commands.py) | 指令存储 + 状态机 + 超时看门狗 |
| [`week1/server/server.py`](../../week1/server/server.py) | 新增 `/api/command*` 路由；在 `/api/data` 响应里捎带指令；处理回执 |
| [`week1/firmware/esp32_imu/main/main.c`](../../week1/firmware/esp32_imu/main/main.c) | 读回响应体、解析指令、执行突发采集、回报执 |
| [`week1/web/index.html`](../../week1/web/index.html) | 「重新采集」按钮 + 四阶段时间线 + 新旧数据区分 |
| [`week1/tools/cmd_selftest.py`](../../week1/tools/cmd_selftest.py) | 无硬件自测（软件模拟板子） |
| [`week1/tools/cmd_acceptance.py`](../../week1/tools/cmd_acceptance.py) | 真机验收，输出完整证据链 |

## 1. 核心难点：「刷新」与「重新采集」的区别

这是本单元最容易含糊过去的地方，所以设计上做成**数据结构层面的可区分**，而不是界面话术。

| | 刷新页面 | 点「重新采集」 |
|---|---|---|
| 客户端行为 | `GET /api/latest`、`GET /api/history` | `POST /api/command` |
| 服务器行为 | 读 SQLite，返回已有行 | **受理**一条指令，入队并等设备执行 |
| 设备行为 | 无 | 取走指令 → 采一批新数据 → 回报 |
| 数据库变化 | **一条都不增加** | 新增 N 条，且 `trigger='command'` |
| 数据的 `request_id` | `NULL` | 该次指令的 id |
| 可证伪点 | 刷新前后 `id` / `seq` / 总条数完全不变 | 总条数增加、`request_id` 可精确回溯到这次点击 |

**关键设计**：每一条被指令触发采集的数据，都带两个新字段：

- `trigger`：`'timer'`（1Hz 常规定时上报）或 `'command'`（指令触发）
- `request_id`：触发它的那条指令 id（定时上报为 `NULL`）

于是"这些数据是这次请求新采的"不是靠时间窗口去猜，而是**数据库里的直接关联**。

## 2. 指令是怎么送达板子的：搭车，而不是推送

板子的 HTTP 客户端**只做 POST、不监听端口**，所以服务器**无法主动推**任何东西给它。

朴素方案都代价不小：

| 方案 | 代价 |
|---|---|
| 板子开一个 HTTP 服务端口等指令 | 要多写一套 server；受第1周那个「单线程 httpd 被推流堵死」的坑连累（见文档 06） |
| MQTT / WebSocket 长连接 | 要引入新协议栈，占内存，破坏"1Hz 短连接"的简单模型 |
| 板子 HTTP 长轮询 | 连接常驻，WiFi 抖动时容易挂着不恢复 |

**采用的方案：搭车（piggyback）**。板子本来就每 1 秒 POST 一次，那就把待执行指令
塞进**这次 POST 的响应体**里：

```
板子 ──POST /api/data──► 服务器
                          │ 有排队中的指令？
板子 ◄──200 {"ok":true,...,"command":{"request_id":"CMD-...","params":{...}}}
      │
      └─► 解析出来 → 立刻执行 → 回报
```

好处：
- 板子**不新增任何端口**，也不引入新协议
- 天然复用现有链路的重试/超时行为，网络抖动不会留下"半死"的连接
- **向后兼容**：不带 `command` 字段的响应，板子照旧什么都不做（旧固件也不受影响）
- 代价：指令送达有**最多 1 秒延迟**（等下一次上报）。对本场景完全够用

> 这个取舍写在这里是有意的 —— 如果以后要做**秒级以下**的实时控制（比如急停），
> 1 秒延迟不可接受，那时才值得引入 WebSocket/MQTT。现在不该为不需要的东西付复杂度。

## 3. 状态机

```
                  POST /api/command
                         │
                    ┌────▼─────┐
                    │  issued  │   ① 服务器受理
                    └────┬─────┘
        下次上报时随响应捎带 │
                    ┌────▼──────┐
                    │ delivered │   ② 指令已下发到板子
                    └────┬──────┘
        板子回报 cmd_state=received
                    ┌────▼──────┐
                    │ received  │   ③ 设备接收，开始执行
                    └────┬──────┘
        板子回报 cmd_state=done
                    ┌────▼─────┐
                    │   done   │   ④ 执行完成，新数据已入库
                    └──────────┘

  任一阶段超时 ──► timeout（并记录 timeout_stage = accept | exec）
  执行中出错   ──► failed（带 note 说明原因）
```

实现要点（都在 `commands.py`）：

1. **状态只进不退。** `_advance()` 用 `ORDER.index()` 比较，重复上报（网络抖动导致
   `received` 重发）不会把状态从 `done` 打回 `received`。
2. **终态冻结。** `done` / `timeout` / `failed` 之后不再接受任何状态改动。
3. **超时分两段，并记录卡在哪一段。** 这是诊断价值的核心：
   - `accept`：指令发出去后板子一直没来取 → 板子掉线 / 重启 / 没在上报
   - `exec`：板子取走了但没执行完 → 执行中崩了 / 上报通道断了
4. **`pending_for()` 取出即标记 `delivered`。** 所以同一条指令不会被重复下发。
5. **超时由服务器主动落库**（后台线程每秒扫一次），不是查询时顺手算的 ——
   否则"超时"这件事在数据库里就没有服务器侧的证据。

### 阶段耗时（`to_public()` 算好给网页直接用）

| 字段 | 含义 |
|---|---|
| `issue_to_deliver_ms` | 受理 → 下发（主要受"等下一次 1Hz 上报"影响，正常 ≤ 1000ms） |
| `deliver_to_receive_ms` | 下发 → 设备确认接收（一次 HTTP 往返，几十毫秒量级） |
| `receive_to_done_ms` | 确认 → 采集完成（≈ samples × interval_ms） |
| `total_ms` | 端到端 |

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/command` | 下发指令。body: `{device_id, type:"recollect", samples, interval_ms}` → `202 {request_id, status:"issued", accept_timeout_s, detail_url}`；`type` 另可为 `pause` / `resume` |
| GET | `/api/command/<id>` | 指令详情：状态、各时间点、各阶段耗时、失败原因（`note`）、新采集条数与 id 范围 |
| GET | `/api/commands?limit=N` | 最近指令列表（验收时看整条链） |
| POST | `/api/poll` | **暂停期间的心跳**：不写 `readings`，只为把待执行指令捎带回去（见 §8.1） |

参数服务端会限幅：`samples ∈ [1,100]`、`interval_ms ∈ [20,1000]`；固件里**再挡一层**
（`samples ≤ 200`），避免异常参数把主循环卡死。

板子回执复用现有接口，不新增路由：

```
POST /api/data  body 里带 request_id="CMD-..."，
                cmd_state="received" | "done" | "failed"（可再带 cmd_note 说明原因）
```

> `type` 加白名单：拼错当场 `400` 并回可用类型，而不是受理一条板子永远不认识的指令、
> 白等 30 秒超时。

## 5. 固件侧的改动

### 5.1 必须把响应体读回来

原来用 `esp_http_client_perform()`，它**把响应体丢掉了**。改成显式流程：

```c
esp_http_client_open()      // 建立连接，声明要写 len 字节
esp_http_client_write()     // 发送请求体
esp_http_client_fetch_headers()   // 读响应头，拿到 Content-Length
esp_http_client_read()      // 读响应体 —— 指令就在这里
esp_http_client_close()
```

响应体给 512 字节缓冲（实际几十到两百字节）。

### 5.2 解析用 IDF 自带的 cJSON

`#include "cJSON.h"`，组件名 `json`。**不需要在 `main/CMakeLists.txt` 写 `REQUIRES`** ——
第 1 周已经踩过这个坑：一旦显式写 `REQUIRES`，就只剩指定的那几个组件，
`esp_wifi.h` 之类会全部找不到（见文档 07 第 8 条）。

### 5.3 采样逻辑抽成 `build_payload()`

第 2 周起同一段采样代码有了**两种触发方式**，所以抽出来带参数：

```c
static int build_payload(char *out, size_t out_sz, uint32_t seq,
                         const char *request_id, const char *trigger,
                         const char *cmd_state);
```

- 定时上报：`request_id=NULL, trigger="timer", cmd_state=NULL`
- 指令采集：`request_id="CMD-...", trigger="command", cmd_state="received"/"done"`

### 5.4 一次指令的执行过程

```
解析出指令
  → 立刻上报一条 cmd_state="received"     （让服务器知道"设备真的收到了"）
  → 按 interval_ms 逐条采集 samples 条，每条都带 request_id
  → 最后一条带 cmd_state="done"           （服务器据此判定完成）
  → 回到 1Hz 定时上报
```

执行期间**不再接收新指令**（`trigger != "command"` 才查队列），避免两条指令交叉执行。

## 6. 网页侧

### 6.1 四阶段时间线

`renderTimeline()` 把四个阶段画成横条，已到达的变绿并显示到达时刻，
当前停在的那一步变黄（超时变红并注明卡在哪一段）。**任何一步卡住都能一眼看出。**

且轮询间隔是 500ms（比主数据轮询快），因为整条链通常 1~2 秒就结束了，
1 秒的轮询会让"推进过程"看不清。

### 6.2 用数字摊开区别

面板底部的对比行会显示：**下发前库里 N 条 → 下发后 M 条（+M−N）**，
以及该指令的 `sample_count`。刷新页面时这两个数不会变 —— 这就是最直接的证明。

### 6.3 表格里标出"指令来的数据"

表格新增「触发」列：`定时` / `指令`（指令行整行高亮），鼠标悬浮显示 `request_id`。
依据是数据自带的 `trigger` 字段，**不是界面上的时间猜测**。

## 7. 已知限制

- **指令送达延迟 ≤ 1 秒**：受 1Hz 上报周期限制，见第 2 节的取舍说明。
- **板子离线时指令只能超时**：没有离线补发机制。板子重连后不会去补"历史指令"，
  因为一条过期的采集请求本身就没有意义了。
- **单设备并发未做优先级**：同一设备多条指令按 FIFO 顺序执行，没有优先级/取消。
- **指令只在内存 + SQLite 里，没有鉴权**：同网段任何人都能下发指令（课程内部使用可接受）。

## 8. 后续补齐（2026-09-23，对照任务卡原文）

按任务卡逐条核对后，本篇相关的有三项之前漏做或只做了一半，均已补齐并真机验证。
**状态本身的定义**（六态、谁能推进、为什么 `failed` 与 `timeout` 必须分开）
见 [`10-指令状态机与状态图.md`](10-指令状态机与状态图.md)；这一节只讲实现。

### 8.1 暂停周期上报 —— 用心跳保住命令通道

任务卡两处要求「暂停周期上报、保持命令通道」。矛盾在于：指令靠搭车在
**板子自己上报请求的响应体**里下发，上报一停通道就断了。

```
正常：POST /api/data   写一条记录 + 取指令
暂停：POST /api/poll   一条都不写  + 取指令
```

- 新增 `POST /api/poll`：**不写 `readings`**，只更新设备在线状态与 `paused`，
  然后把待执行指令照常捎回去。
- 固件：`SERVER_URL` 拆成 `SERVER_BASE` + `PATH_DATA` / `PATH_POLL`；
  新增 `s_paused`、`dispatch_command()`、`poll_tick()`。
- 控制类指令（`pause`/`resume`）的回执**分两次发**（`received` → `done`）：
  一条请求只能带一个 `cmd_state`，分两次才能让四阶段证据链与采集指令完全一致，
  网页不必为控制类指令写特殊分支。
- `/api/latest` 与 `/api/devices` 带出 `paused`。**少了它网页只有一个"数据年龄"可用**，
  会把"我们主动让设备别上报"错判成"设备掉线" —— 那是冤假错案。

### 8.2 `failed` 从此有了真实路径

原先 `failed` 在状态机里定义、网页也能渲染，但**没有任何代码会设置它** —— 死代码。
现在：

- 固件把「采集」与「结论」**分成两次独立回报**：样本本身不带 `cmd_state`，
  采完再单独发一条结论，`cmd_state = done | failed` + `cmd_note` 说明原因。
  为什么要分开：如果结论搭在最后一条样本上，整批被拒绝时结论就永远送不出去，
  服务器只能一路等到 `exec` 超时 —— 于是「设备明确说它失败了」和「服务器什么都没听到」
  被混成同一件事，而这正是 `failed` 与 `timeout` 该分开的意义。
- 服务器 `_apply_cmd_receipt()` 接受 `failed`，转 `mark_failed()` 并把原因写进 `note`。
- 顺带修了两处：`mark_done()` 支持 `note`（"完成但没完成干净"，例如 8 条里只送达 6 条，
  完成就是完成、不降级，但代价必须写下来）；网页时间线第 4 步从「执行完成」
  改名为「**执行结果**」（它本来就有三种结局，名字里预设"完成"会在失败时自相矛盾）。

### 8.3 重复点击的闸门 + 重复回执的幂等

两个不同的问题，容易混成一个：

| | 问题 | 处理 |
|---|---|---|
| **重复下发** | 连点 5 次会排队 5 条，最后一条几十秒后才执行 | `POST /api/command` 先查同类在途指令，有就 **409** 并带上那条的 `request_id` |
| **重复回执** | 设备重试结论上报（服务器其实已入库），会留下多条一模一样的记录 | 同一 `request_id` + 同一终态 `cmd_state` 已存在时，返回 `{"duplicate":true}` 且**不再入库** |

- 闸门按「**同类**」判定，不按设备全局判定 —— 采集在途时点「暂停」必须放行。
- 闸门**必须在服务器**：界面上的 `disabled` 拦不住"两个标签页同时点"。
- 幂等判定很窄，只覆盖 `done`/`failed`：终态在状态机里本来就冻结了，
  第二条不携带任何新信息。（与 `/api/poll` 不写 `readings` 同理：没信息的请求不留痕。）
- 重复回执不是假想：实测中服务器返回 200 已入库，而板子那边
  `esp_http_client_fetch_headers()` 判为失败（串口日志记 `上报失败 HTTP -1`），
  于是同一条 `failed` 被发了 3 次，库里出现 3 条一样的记录，`sample_count` 变成 3。
  **上报是"发出去"和"收到回应"两件事，中间断了设备就分不清服务器处理没处理**
  （两将军问题）—— 所以设备必须重试，而服务器必须对重试免疫。
