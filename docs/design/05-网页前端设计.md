# 05 · 网页前端设计

实现文件：[`week1/web/index.html`](../../week1/web/index.html) —— **单文件、无构建步骤、无 CDN、无框架**，纯原生 HTML/CSS/JS。

## 1. 为什么不用框架

课程环境的网络不可靠（实测连 GitHub 都会 502），机器上的网络也不一定允许访问 CDN。
**无 CDN 依赖**意味着把文件拷到任何地方双击就能打开，不会因为拉不到 `vue.min.js` 而白屏。

趋势曲线用原生 `<canvas>` 手绘，不引入图表库。

## 3. 关键配置常量

```javascript
// API 基址：优先用当前页面的 origin
// 如果页面被当成静态文件直接打开（file:// 或别的静态预览端口），
// 就退回到 127.0.0.1:8000
const API_BASE = (location.protocol === 'http:' || location.protocol === 'https:')
  ? location.origin
  : 'http://127.0.0.1:8000';

// 摄像头模式：'server' = 走服务器中继（默认）；'direct' = 直连板子（仅排障用）
const CAM_MODE = 'server';
const CAM_BASE = 'http://10.1.41.160:81';
const CAM_STREAM    = CAM_MODE === 'server' ? API_BASE + '/api/camera'        : CAM_BASE + '/stream';
const CAM_HEARTBEAT = CAM_MODE === 'server' ? API_BASE + '/api/camera/status' : CAM_BASE + '/ping';
```

> 修过的 bug：原来用相对路径 `/api/*`，当页面被 IDE 以静态预览方式打开（端口 60243）时，请求会打到静态服务器上而不是 8000 端口，表现为「无法连接服务」。固定 `API_BASE` 后解决。

## 4. 数据轮询与「未更新」提示

```
每 1 秒：GET /api/latest
   │
   ├─ 拿到记录 → 更新卡片数值、合加速度、温度、内存、RSSI、表格
   ├─ age_seconds > STALE → 状态胶囊变红，显示「未更新 · 已 N 秒」
   └─ 数值冻结在最后一次的值，时间保留最后的 server_ms
```

设计上**页面不自己倒计时**，每轮都用服务器返回的 `age_seconds` —— 这样显示的时间永远与服务端一致，且能同时反映「板子停了」和「服务器停了」。

## 5. 性能优化（第二轮重写时加入）

| 问题 | 做法 |
|---|---|
| 每秒重设 `canvas.width` 会重新分配画布，卡顿 | 改用**数据签名**（id 首尾）+ 尺寸双重判定，未变化则**跳过重绘** |
| 请求可能挂住 | 加 6 秒超时 `AbortController` |
| 后台标签页空转 | 标签页不可见时**暂停轮询**，切回立即补一次 |
| 静默失败 | `fetch` 检查 `r.ok`，失败不当作成功 |
| 重连时浏览器缓存住失败状态 | 重连 URL 必须带 `?nocache=Date.now()` |

## 6. 卡片与表格

- 主区 **3 列 6 张卡片**：加速度 X / Y / Z、合加速度 |a|、芯片温度、剩余堆内存；再单独一张 WiFi 信号卡片（共 4 列布局）。
- 堆内存卡片带 `.sub` 副行「已用 X MB / 共 Y MB」，`title` 悬浮显示**历史最低水位**（持续下降 = 疑似内存泄漏）。
- 表格列：id / 时间 / 序号 / ax / ay / az / |a| / 温度 / 剩余MB / 已用MB / 来源IP（`colspan` 随列数变动维护）。
- 缺数据时显示「—」而不是 0：

```javascript
const fmt = (v, n = 3) => (v === null || v === undefined) ? '—' : Number(v).toFixed(n);
const mb  = (b) => (b === null || b === undefined) ? '—' : (Number(b) / 1048576).toFixed(2);
const num = (v) => (v === null || v === undefined) ? null : Number(v);
```

老固件不上报 `total_heap` 时，「已用 / 共」显示「—」，不硬算成 0。

## 7. 角速度的移除

**QMA6100P 只有三轴加速度计，没有陀螺仪**，`gx/gy/gz` 恒为 0。第二轮重写时做了以下清理：

- 删掉 3 个角速度卡片
- 删掉曲线切换按钮（加速度/角速度）与 `gyr` 序列
- 删掉表格里的 `gx/gy/gz` 列
- 清理掉全部 `data-page-node-id` 噪音属性
- 新增「合加速度 |a|」卡片与表格列

固件与数据库仍保留 `gx/gy/gz` 字段（恒 0，无害），彻底清需改固件重烧 + 改表。

> 顺带确证：QMA6100P 官方 datasheet 明确为 *three-axis accelerometer*。网上若干页面称其为「6 轴 IMU 带陀螺仪」是 AI 生成的错误信息（连封装都误写成 LGA-14，官方是 LGA-12），不可信。

## 8. CSV 下载

```javascript
// 直接让浏览器下载，不用 fetch + Blob —— 几万条不占内存
window.location.href = API_BASE + '/api/export.csv';
```

范围下拉 `#csvRange` 提供：最近 100 / 1000 条、最近 1 / 6 / 24 小时、最近 3 / 7 天、全部记录。选「全部」时不传参，走服务端默认上限。

表格标题右侧显示「累计 N 条（上限 M）」，启动时通过 `/api/devices` 汇总。

## 9. 摄像头区块

见 [`06-摄像头链路与视频中继.md`](06-摄像头链路与视频中继.md)。要点：

- `<img src>` 直接指向 MJPEG 流地址，靠浏览器原生 multipart 解码
- **每 3 秒 `/ping` 心跳**：两次失败 → 判死自动重建；`clients=0` 但自己以为还在看 → 判定画面已冻结，同样重建
- 失败退避重试（2s 递增到 10s，20 次后提示重新上电）
- 心跳解析兼容 server / direct 两种模式（server 读 JSON 的 `state` / `last_frame_age`，direct 读板端 `clients=N`）

### 10.1 设计令牌化（深色模式的前提）

改版前样式里散着二十多个写死的色值（`#faf9f6` / `#f1efe8` / `#0f6e56` …），
同一个"浅灰底"在 6 处各写一遍。**这种写法没法加深色模式** —— 一改就得逐处找，
漏一处就是深底上蹦出一块浅色。

现在全部收成语义变量（`--surface-2` / `--ok-fg` / `--s-ax` …），
深色模式只需要在 `@media (prefers-color-scheme: dark)` 里重定义这一组值。
`color-scheme: light dark` 让原生控件（下拉框、滚动条）也跟着走，不用手动重画。

落地时用脚本做批量替换并**断言每一条的命中次数**，不是手工逐处改：
一次替换如果在文件里命中了 0 次或 3 次（预期 1 次），脚本直接报错退出、不写文件。
这次真的拦住了两次写错模式的替换 —— 没断言的话，改出来的是"报成功但没落盘"。

画布上的颜色走 `getComputedStyle` 读变量。canvas 不认 CSS 变量，
所以系统切换深浅色时要重读一遍再重画（`matchMedia` 监听），
这是用变量做主题唯一的额外成本。

### 10.2 信息层级：把推导过程折起来，结论留在外面

两处长说明改成了 `<details>`。原则是 **summary 里留一句结论，只折叠推导过程** ——
全折起来等于把信息藏了。

同时发现一个真问题：`#cmdHint` 原本既承担"静态说明"又承担"实时状态"。
JS 一下发指令就把那段说明覆盖掉了，等于**说明只能看一次，之后再也读不到**。
现在拆开：状态行归状态行，说明进折叠块。

卡片区按**回答的问题**分成两组，各加一行小标题：

- `被测对象 · 板载 QMA6100P 三轴加速度` —— 这次实验在测什么
- `设备自身状态 · 数据断流时先看这一组` —— 出问题先查哪里

改版前 7 张平铺，"芯片温度"和"加速度 X"看起来同等重要。

### 10.3 趋势图

四项改动，每一项都对应一个具体缺陷：

**① 时间窗（1 分钟 / 10 分钟 / 1 小时）** —— 原来固定 60 条，
标题写着"趋势"却只有一个窗口。

这里踩到一个值得记的坑：**加时间窗时用的是"取最近 N 条"**，
而设备一旦有离线空档，N 条就可能横跨很久 —— 实测 `limit=3600` 返回的 3600 条
**跨了 4.6 天**。那会变成界面写着"最近 1 小时"、画的却是 4 天，
又是一条"看着对其实是错的"证据。所以给 `/api/history` 加了 `minutes` 参数，
**时间范围由服务器按时间过滤**，`limit` 只当安全上限。
（服务端 `limit` 上限同时从 500 提到 4200，否则 1 小时档静默地只剩 8 分钟数据。）

**② 横轴按真实时间定位，空档处断开曲线** —— 原来按下标均分。
设备离线的那段会被压缩成一条水平直线，看起来像"这段时间一直是这个值"，
而事实是这段时间根本没有数据。现在相邻两点时间差超过"正常间隔的 5 倍"
（且至少 3 秒）就把曲线断开。

**③ 纵轴最小跨度 0.25 g** —— 这条是**修一个显示失真**：
板子静止时三轴只有约 ±15 mg 的本底噪声，而原来的自动缩放会把这 0.06 g
撑满整个图高，看起来像剧烈抖动 —— **把正常的物理噪声显示成了故障**。

注意这里**刻意没有**用分位数裁掉极值。那是"只要主趋势"的场景才合适；
本页面盯的正是加速度峰值，把尖峰裁掉等于把最该看见的东西藏起来。

**④ 悬停读数** —— 十字线 + 数值框，画在**单独一层画布**上。
数据层不重画（重复设 `canvas.width` 会清空并重新分配位图，鼠标一动就卡）。
读数框靠右时自动翻到左侧，免得被画布边缘截掉。

点数超过像素列数时（1 小时档 3600 点 vs 约 900 像素宽）按**像素列**归并，
每列画一条 min→max 竖线段 —— 形状和峰值都保住，只丢掉列内先后顺序。

### 10.6 两条教训

**① 看图的判断不可靠，用像素说话。** 用 CDP 模拟深色后，
页面里 JS 回读 `getComputedStyle(document.body).backgroundColor` 明确是
`rgb(25,25,23)`，但截图我看着还是浅色，白花时间去找 CSS 的问题。
写了 `img_sample.py` 直接解 PNG 采样：平均亮度 **36.8 vs 243.3**，
背景确实是 `rgb(25,25,23)` —— 深色**一直是生效的**，是我的目视判断错了。

**② 一个永远为真的检查等于没有检查。** 审计脚本第一版里，
"没有 JS 报错"读的是一个**从没被写入过的列表**，所以它必然通过 ——
跟本项目一直在防的"看起来对的错误证据"是同一类东西。
现在改成：加载前用 `Page.addScriptToEvaluateOnNewDocument` 装错误监听，
并且**先故意抛一个错验证探测器本身有效**，再清空、再看真实报错。
（这个做法是照搬第 2 周失败态验证的思路：撤掉故障注入后同一块板子能跑通，
没有这个对照就排除不了"板子有病"。）

## 11. 分区标签页（2026-09-28 第二轮，用户反馈之后）

第一轮"精修"做完，用户的原话是：

> 我看这也没有变化，可以分类，全部都放到一个界面是不是太臃肿了

**两个判断都对。**

- 第一轮只动了样式和信息层级，**没动结构** —— 用户上一条选的是"保持现有风格精修"，
  我就没敢重排版式，结果视觉上几乎看不出区别。这是理解偏了：他要的不是"更精致的同一页"。
- 真正的病灶是一页塞四件事：实时数据 / 下发指令 / 教学求助 / 摄像头 / 历史数据
  竖着堆到 2400px 以上。**想看求助要滚过摄像头，想点采集要滚过求助。**

### 11.1 分区怎么切的

| 分区 | 内容 | 回答的问题 | 页高 |
|---|---|---|---|
| **概览**（默认） | 卡片 + meta + 趋势图 | 设备现在怎么样 | 865 px |
| **交互** | 指令面板 + 四阶段时间线 | 让设备再采一次 | 400 px |
| **求助** | 教学求助面板 | 有人按了键，我要回应 | 820 px |
| **影像** | 摄像头 | 现场画面 | 482 px |
| **数据** | 表格 + CSV 导出 | 翻历史 / 拿走数据 | 604 px |
| **全部** | 以上全部 | 验收、演示要看全貌 | 2521 px |

参照：改版前未分区时整页 **2743 px**。各分区页高是同一次浏览器会话内量出来的，可直接比较。

保留「全部」这个分区是有意的：分区解决了"臃肿"，但验收和演示时往往需要一次性看全貌，
并且要能看到各个证据之间的对应关系。

### 11.2 分区带来的三个连带问题（都必须处理）

**① 曲线在隐藏分区里量不到宽度。**
canvas 放在 `display:none` 的容器里时 `clientWidth` 是 0，
而原来的 `cv.clientWidth || 900` 会**真的按 900px 画一张图**（还每秒重画一次），
切回来再被拉伸变形。现在宽度为 0 时直接跳过绘制，
切到可见分区时由 `applyTab()` 强制重画一次。

**② 藏起来的面板会丢掉「有人在求助」这个信号。**
这是分区最危险的副作用：第 3 周做的整件事（按键发起求助 → 有人回应）靠的就是"看得见"，
面板一藏等于把核心功能废掉 —— 别人按了键、页面开着，却没人知道要去看。
所以顶部标签加了徽标：有待回应的求助时「求助」上显示数字。
同理，指令在途时「交互」上点一个小圆点。

**③ 测试会变成假通过。**
原来两个浏览器实测都用 JS 的 `.click()` 点按钮 ——
而 `.click()` 对**隐藏元素照样生效**，所以即使按钮根本点不到，测试也照样"通过"。
现在两个脚本都改成：**先切到对应分区，再断言元素真的可见**
（`getBoundingClientRect().width > 0`），不可见就直接判测试无效。

### 11.3 顺带发现并修掉的一个真 bug

徽标用 `hidden` 属性控制显隐，但 CSS 里给它写了 `display: inline-flex`。
**UA 样式里的 `[hidden]{display:none}` 优先级低于任何带 `display` 的作者样式** ——
于是 `hidden` 静默失效，徽标**永久显示"0"**：在一个最不该误报的地方挂了个永久假警报。

修法是全局加一条 `[hidden] { display: none !important; }`。

发现它的过程同样值得记：审计脚本原本只测"造一条求助之后徽标会不会亮"，
而"永远亮着"**同样能通过那个检查**。现在改成**两个状态都测** ——
先比对接口的真实待回应数与界面徽标是否一致，再造事件看它会不会亮。

### 11.4 实现取舍

- **显隐规则全写在 CSS 里**（`body[data-tab="help"] #panel-help { display: block }`），
  JS 只改 `body` 上的一个属性。逐个元素 toggle 的话，分区一多就容易出现
  "两个同时可见"或"都不见"，而且只在特定点击顺序下复现，很难查。
- **用 URL hash 而不是纯内存状态**：刷新 / 分享链接能落在同一个分区
  （验收时可以直接给人 `#help`），浏览器前进后退键也能用。
- **结构切分用脚本做**，不用手工编辑：切块要数嵌套的 `<div>`，而这个文件里有
  10 处 `<div class="chartbox">` / `charthead` 混在一起，手工极容易少切一个 `</>`。
  脚本用**配对计数**找块尾，并在每一步 `assert`，切错就整体不写。
