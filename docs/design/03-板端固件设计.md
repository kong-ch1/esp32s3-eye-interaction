# 03 · 板端固件设计

工程位置：[`week1/firmware/esp32_imu/`](../../week1/firmware/esp32_imu/)（ESP-IDF 5.4.4）

另有最小学习工程 [`week1/learn/step1_imu/`](../../week1/learn/step1_imu/)：只读 IMU 并串口打印，用于逐步理解每一行代码，不含 WiFi/HTTP/摄像头。

## 1. 主循环做什么

```
app_main()
  │
  ├─ nvs_flash_init()
  ├─ i2c_master_init()            GPIO4/5, 400kHz, I2C_NUM_0
  ├─ i2c_scan()                   打印总线上所有设备（调试用）
  ├─ qma6100p_init()              软复位 → 退出睡眠 → 设量程/带宽 → 回读确认
  ├─ imu_identify()               型号自检，打印证据链
  ├─ temp_sensor_init()           TSENS，量程 -10~80°C
  ├─ wifi_init_sta()              连 WiFi（已关 Modem-sleep）
  ├─ camera_stream_start()        摄像头 MJPEG 流服务（失败只告警，不阻断上报）
  │
  └─ while (1) {                  每 1000 ms 一轮
         读 6 字节加速度原始值
         → qma_assemble14() 组装 14 位补码
         → 减零偏、乘灵敏度、Z 轴乘标定系数
         → 读芯片温度 / 剩余堆 / 历史最低堆 / 总堆 / RSSI
         → 拼 JSON
         → HTTP POST /api/data（超时 2 秒）
         vTaskDelay(1000ms)
     }
```

## 2. 加速度计驱动

### 2.1 初始化顺序（顺序错了就不工作）

```c
1. 软复位：写 0x36 = 0xB6，延时 20ms，再写 0x36 = 0x00
2. 退出睡眠：写 0x11 = 0xC0（POWER 寄存器，主动模式）
3. 设量程：  写 0x0F = 0x01（±2g）
4. 设带宽：  写 0x10 = 0x05（1024Hz）
5. 回读 0x0F/0x10/0x11 确认写入生效
```

**为什么第 1 步必须有**：本板上电后寄存器写入不生效、**Y 轴数据冻结在 -FS**。软复位后才恢复正常。`0x36` 正是 QMA6100P 的 `SW_RESET` 寄存器 —— 这在 QMA7981 手册里根本不存在，是型号勘误的直接后果。

### 2.2 数据组装

```c
/* MSB 寄存器 = DX[13:6]，LSB 寄存器 bit5:0 = DX[5:0]，bit7 = NEWDATA 标志
 * 14 位二进制补码，bit13 为符号位 */
static inline int16_t qma_assemble14(uint8_t lsb, uint8_t msb)
{
    int16_t v = (int16_t)(((uint16_t)msb << 6) | (lsb & 0x3F));
    if (v & 0x2000) v -= 0x4000;
    return v;
}
```

> `learn/step1_imu` 里最初写的是 `(msb << 6) | (lsb & 0x3F)`，后来按 datasheet 改为 `lsb >> 2`。两者只差最低 6 位（约 0.01g 量级），实测模长没有变化 —— 当时观察到的 `|a| ≈ 0.64g` 经确认是**板子没放平**，不是代码问题。

### 2.3 标定与换算

```c
#define QMA_SENS_LSB_PER_G  4096.0f   /* ±2g、14位 */

#define CAL_X_OFF    2265.0f   /* 0.553g * 4096 */
#define CAL_Y_OFF     608.0f   /* 0.148g * 4096 */
#define CAL_Z_OFF    1594.0f   /* 0.389g * 4096 */
#define CAL_Z_SCALE    0.912f
```

换算：`accel_g = (raw - OFF) / 4096 * (轴 == Z ? CAL_Z_SCALE : 1.0)`

标定值来自**旋转实验两点法**（面朝上 / 朝下静止各测一组，解零偏与灵敏度）。标定后各静置姿态模长 0.97~1.01 g。换板子必须重新标定。

## 3. 数据上报

### 3.1 JSON 字段

| 字段 | 含义 | 备注 |
|---|---|---|
| `device_id` | 设备标识 | `team01-esp32s3eye` |
| `seq` | 递增序号 | 用来判断板子是否有发（seq 跳号 = 板子没发出去） |
| `ax/ay/az` | 三轴加速度（g） | 已标定 |
| `gx/gy/gz` | 三轴角速度 | 恒为 0（硬件无陀螺仪），保留字段 |
| `device_ms` | 上电毫秒数 | 板子无 RTC，只能算间隔 |
| `temp_c` | 芯片温度（°C） | 读不到时发 JSON `null`，不发 0 |
| `free_heap` | 当前剩余堆 | `esp_get_free_heap_size()` |
| `min_free_heap` | 历史最低堆水位 | 持续下降 = 疑似内存泄漏 |
| `total_heap` | 堆总大小 | `heap_caps_get_total_size(MALLOC_CAP_DEFAULT)` |
| `rssi` | WiFi 信号强度（dBm） | `esp_wifi_sta_get_ap_info()`，失败发 null |

### 3.2 POST 超时设为 2 秒

```c
esp_http_client_config_t cfg = {
    .url = SERVER_URL,
    .method = HTTP_METHOD_POST,
    .timeout_ms = 2000,   /* 原为 5000 */
};
```

**为什么**：WiFi 差时 HTTP 会一直卡到超时才失败，**卡多久 = 主循环停多久 = 丢多少条数据**。5 秒超时意味着网络一抖就连续丢 5 条。改成 2 秒后快速失败，下一轮立刻重试，空洞反而更小。

## 4. 设备自身状态上报

### 4.1 芯片温度（TSENS）

ESP32-S3 内置温度传感器，无需外接元件。测的是**芯片裸片温度**，不是环境温度 —— 芯片自身发热，通常比室温高几度，适合观察负载/温升趋势。

> **⚑ 大坑：量程必须完整落在预定义档位内**
>
> ESP32-S3 只有 5 个档位（见 `components/soc/esp32s3/temperature_sensor_periph.c`）：
>
> | 档位 | 范围 | 精度 |
> |---|---|---|
> | 1 | 50 ~ 125 °C | |
> | 2 | 20 ~ 100 °C | |
> | 3 | **-10 ~ 80 °C** | **误差 ±1（最准）** |
> | 4 | -30 ~ 50 °C | |
> | 5 | -40 ~ 20 °C | |
>
> 当初填 `-10 ~ 110`，**没有任何一个档位能覆盖这个区间**，`temperature_sensor_install()` 直接返回 `ESP_ERR_INVALID_ARG`，日志报 `Out of testing range`。改为 `TEMPERATURE_SENSOR_CONFIG_DEFAULT(-10, 80)` 后正常，实测读到 44~47 °C。

### 4.2 堆内存统计

```c
esp_get_free_heap_size()          // = heap_caps_get_free_size(MALLOC_CAP_DEFAULT)
esp_get_minimum_free_heap_size()  // = heap_caps_get_minimum_free_size(MALLOC_CAP_DEFAULT)
heap_caps_get_total_size(MALLOC_CAP_DEFAULT)   // 总堆，口径必须一致
```

> **⚑ 口径要点**：前两个函数内部都是 `heap_caps_get_*_size(MALLOC_CAP_DEFAULT)`，所以「总堆」必须用**同口径**的 `heap_caps_get_total_size(MALLOC_CAP_DEFAULT)`，否则「总 − 剩余」算出的已用值会离谱。需 `#include "esp_heap_caps.h"`。
>
> **实测**：total = 8 716 204 B（8.31 MB）/ free = 8 527 192 B（8.13 MB）→ 已用 0.18 MB。
> ESP32-S3-EYE 有 8MB PSRAM 并入默认堆，所以总量是 8MB 量级，而不是内部 SRAM 的几百 KB。

### 4.3 WiFi 信号强度

```c
wifi_ap_record_t ap;
if (esp_wifi_sta_get_ap_info(&ap) == ESP_OK) rssi = ap.rssi;
```

实测本板 RSSI 为 **-32 ~ -38 dBm**（极强），用于排除「信号弱导致断流」这一假设。

### 4.4 关闭 WiFi 省电

```c
esp_wifi_set_ps(WIFI_PS_NONE);
```

默认 Modem-sleep 下板子周期性休眠，AP 只能先缓存包、等板子醒了再发，导致延迟动辄几百毫秒到几秒并伴随丢包。数据上报是持续业务，这点电不值得省。

## 5. 编译配置（sdkconfig）

### 5.1 必改项

| 配置 | 值 | 原因 |
|---|---|---|
| `CONFIG_IDF_TARGET` | `esp32s3` | **板子是 S3，不是 esp32**。错了能编过但行为全错 |
| `CONFIG_SPIRAM` | `y` | 一帧 320×240 就是 150 KB，内部 DRAM 只有 200 多 KB，**不开必崩** |
| `CONFIG_SPIRAM_MODE_OCT` | `y` | 板载是 Octal PSRAM |
| `CONFIG_SPIRAM_SPEED_80M` | `y` | |
| `CONFIG_SPIRAM_USE_MALLOC` | `y` | 让 PSRAM 并入默认堆 |
| `CONFIG_ESPTOOLPY_FLASHSIZE_8MB` | `y` | |
| `CONFIG_ESP_MAIN_TASK_STACK_SIZE` | `8192` | 原 3584（3.5 KB）跑 HTTP/LwIP 极易栈溢出 |
| `CONFIG_SCCB_HARDWARE_I2C_DRIVER_LEGACY` | `y` | **摄像头必需**，见下 |
| `CONFIG_LWIP_MAX_SOCKETS` | `16` | 原 10，MJPEG 多客户端不够用 |
| `CONFIG_LWIP_TCP_KEEPALIVE` | `y` | 配合 KEEPIDLE=15 / KEEPINTVL=5 / KEEPCNT=3 |

> **⚑ 大坑：不要在 `main/CMakeLists.txt` 里加 `REQUIRES esp_driver_tsens`！**
> ESP-IDF 中组件**不写 `REQUIRES` 时默认纳入所有组件**；一旦显式指定，就只剩指定的那几个，导致 `esp_wifi.h` / `esp_timer.h` 全部 not found（`BUILD_EXIT=2`）。温度头文件本来就在默认依赖里，**不需要声明**。

### 5.2 自定义分区表

原默认分区表 app 分区只有 1MB，装不下「摄像头 + WiFi + HTTP」的固件。自定义 `partitions.csv`：app 分区从 `0x10000` 起，大小 **`0x400000`（4MB）**。

### 5.3 组件依赖

`main/idf_component.yml`：

```yaml
dependencies:
  espressif/esp32-camera: "^2.1.1"
```

实际拉取到 esp32-camera 2.1.7 + esp_jpeg 1.3.1。

> **网络要点**：PowerShell 的 `Invoke-WebRequest` 连 GitHub 失败（代理 CONNECT 返回 502），手动猜组件仓库 API 路径也全是 404。**正确做法是让 IDF 组件管理器自己下载**（`run_idf.py reconfigure`），它能连通。

### 6.1 硬复位与「卡 download 模式」的处理

USB-JTAG 下控制线映射：**DTR = GPIO0(IO0)，RTS = EN**

| 目的 | 序列 |
|---|---|
| 进下载模式 | `DTR=True`（IO0=0）+ RTS 脉冲 |
| 正常运行（硬复位） | 保持 `DTR=False`，RTS 脉冲：`RTS=True → sleep 0.2 → RTS=False` |

> 踩过的坑：曾长时间读串口 0 字节输出，`idf_monitor` 显示 `boot:0x0 (DOWNLOAD(USB/UART0))` + `waiting for download`。原因不是复位序列写错，而是**板子本身卡在 download 模式**（疑似 GPIO0 被拉低）。用户拔插 USB 后恢复，同一复位序列随即生效。
>
> 注意：Windows 上 DTR 的变化只在设置 RTS 时才传播。
> 另注意：pyserial 打开 COM 口会拉 DTR/RTS，**等于顺手给板子复位**（诊断时相当于自动做了一次干净基线）。
