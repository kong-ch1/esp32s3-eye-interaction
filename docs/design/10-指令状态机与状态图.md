# 10 · 指令状态机与状态图（首版）

> 任务卡在「第2周 · 后2学时」明确要求产出**首版状态图**，这一份就是。
> 与 [`08-下行指令与回执状态机.md`](08-下行指令与回执状态机.md) 的关系：
> 08 讲的是**怎么实现**（搭车下发、超时看门狗、数据层如何区分刷新与新采集），
> 本篇是**状态本身的定义**——有哪些状态、谁能推进它、终态为什么是这三个。

## 1. 为什么需要一张状态图

因为「网页点一下 → 板子采一批数据」表面上是一条直线，实际上**中间任何一段都可能断**，
而每一段断掉的原因、该查的地方、以及能拿出什么证据，全都不同：

- 指令发出去了，板子没来取（掉线/重启）——**查网络**
- 板子取走了，执行到一半崩了——**查设备**
- 板子明确说「我试了，没干成」——**查设备，且原因在它手里**
- 全都成功了——**看数据**

如果把这些统统收敛成「成功 / 失败」两个状态，验收时就没法回答
「到底卡在哪一步」——任务卡把证据链列为评分重点，正是指这个。

## 2. 状态图

```
                        网页/操作者
                             │
                             │  POST /api/command
                             ▼
                    ┌──────────────────┐
                    │      issued      │  ① 服务器受理
                    │  （已受理待下发） │     服务器侧时间戳 created_ms
                    └────────┬─────────┘
                             │  板子下一次 POST /api/data（或暂停期间的 /api/poll）
                             │  指令搭在该请求的**响应体**里下发
                             ▼
                    ┌──────────────────┐
                    │    delivered     │  ② 指令已下发
                    │  （已交给设备）   │     服务器记录 delivered_ms
                    └────────┬─────────┘
                             │  设备解析到指令，回一条
                             │  cmd_state="received"
                             ▼
                    ┌──────────────────┐
                    │    received      │  ③ 设备已接收
                    │  （设备开始执行） │     设备侧亲口确认
                    └───┬──────────┬───┘
                        │          │
        设备回报 done    │          │   设备回报 failed
        （可能带备注：   │          │   （必带原因，见 §4）
          "部分送达"）   │          │
                        ▼          ▼
              ┌──────────────┐  ┌──────────────┐
              │     done     │  │    failed    │  ④ 执行结果
              │   执行成功    │  │  设备回报失败 │
              └──────────────┘  └──────────────┘
                 ✔ 终态             ✔ 终态

  ── 超时由服务器**主动**判定（后台看门狗每秒扫描），不依赖任何一方的回报 ──

      issued / delivered  ──(accept 超时)──►   ┌──────────────┐
                                              │   timeout    │  ✔ 终态
      received            ──(exec 超时)────►   │ timeout_stage│
                                              │ = accept│exec│
                                              └──────────────┘
```

## 3. 状态表

| 状态 | 含义 | 谁推进它 | 服务器侧证据 | 终态 |
|---|---|---|---|---|
| `issued` | 服务器受理了这条指令，等设备来取 | 服务器（受理瞬间） | `created_ms` | 否 |
| `delivered` | 指令已随某次响应下发出去 | 服务器（取走时**主动标记**） | `delivered_ms` | 否 |
| `received` | 设备明确回报「我收到了，开始干」 | 设备 | `received_ms` | 否 |
| `done` | 设备回报执行完毕 | 设备 | `done_ms` + 新采集记录 | ✅ |
| `failed` | 设备回报「我试了，没干成」+ 原因 | 设备 | `failed_ms` + `note` | ✅ |
| `timeout` | 服务器在期限内没等到下一步 | 服务器看门狗 | `timeout_ms` + `timeout_stage` | ✅ |

**两条硬规则**：

1. **状态只进不退。** 网络抖动会导致设备重复上报，重复的回报不能把已完成的指令打回中间态。
   实现上每次推进都带条件（`_advance()` 只在目标状态更靠后时才更新）。
2. **终态冻结。** 进入 `done` / `failed` / `timeout` 之后一律不再改动。

## 4. `failed` 与 `timeout` 必须分开（这是本版新增的重点）

| | `failed` | `timeout` |
|---|---|---|
| 谁知道结果 | **设备**知道 | **没人**知道 |
| 服务器听到了什么 | 设备明确回报「没干成」+ 原因 | 什么都没有 |
| 该去查什么 | 设备/传感器的执行端 | 网络、供电、设备是否掉线 |
| 页面上怎么显示 | 「设备回报执行失败：8 条全部上报失败」（红色） | 「超时（设备未取走）」（红色） |
| 数据层落点 | `failed_ms` + `note` | `timeout_ms` + `timeout_stage` |

两者在库里落在**不同的列**上，不共用字段——否则排查时就会在错误的方向上浪费时间。

`timeout` 还分两段，因为「设备没来取」和「取了没执行完」是两种完全不同的故障：

| `timeout_stage` | 含义 | 典型原因 |
|---|---|---|
| `accept` | 指令发出去后，设备一直没来取 | 设备掉线、重启、WiFi 断了 |
| `exec` | 设备取走了，但没执行完 | 执行中崩了、上报途中网络断了 |

## 5. 三种触发来源与这张图的关系

板上发生的三件事，落到数据层是三个 `trigger` 值。**不是每种触发都有完整的六态** ——
这一点必须说清楚，否则很容易给实体按键也画一条四阶段时间线，那等于伪造证据。

| 来源 | `trigger` | 起点 | 有状态机吗 | 说明 |
|---|---|---|---|---|
| 板子自己定时上报 | `timer` | 设备 | ❌ | 纯数据，没有「请求」这回事，`request_id` 为 NULL |
| 网页/操作者下发 | `command` | 服务器 | ✅ 完整六态 | 本图的全部内容 |
| 现场的人按实体键 | `button` | 设备 | ❌ | **物理按键没有下行通道**，所以不存在「服务器受理」「指令下发」两步 |

所以网页上：`command` 有四阶段时间线；`button` **只有一条事实记录**（哪个键、几时、采了几条），
不画时间线。

## 6. 并发语义：同一台设备的同类指令，同时只允许一条在途

连点 5 次「重新采集」会怎样？如果不管，服务器会排队 5 条，而设备 1 秒只能取走 1 条：
最后一条要在几十秒后才执行（那时用户早走开了），前面几条还会撞上 `accept` 超时 ——
页面上呈现出一片「完成 / 超时」混杂，看起来像 bug。

**策略**：`POST /api/command` 先查「该设备是否还有同类未走完的指令」，有就返回 **409**，
并在响应里带上那条在途指令的 `request_id`：

```json
{ "error": "busy",
  "existing_request_id": "CMD-20260923-0014",
  "existing_status": "issued",
  "hint": "上一次「重新采集」还没走完（当前 issued），等它结束再点。",
  "detail_url": "/api/command/CMD-20260923-0014" }
```

两个细节：

- **闸门按「同类」判定，不按设备全局判定。** 采集在途时点「暂停」必须放行 —— 把维护类操作
  也一起堵住会很难解释，也会挡住该做的事。
- **网页收到 409 不是弹红字了事**，而是直接接到那条在途指令上继续跟踪。
  用户真正在意的不是「被拒绝了」，而是「我这一下到底有没有生效」。
- **这个闸门必须在服务器**：界面上的按钮 `disabled` 只能管住自己那个标签页，
  拦不住「两个浏览器 / 两台手机同时点」。

## 7. 幂等：重复的终态回执不产生第二条记录

上报是「发出去」和「收到回应」两件事。中间断了，设备就分不清服务器到底处理没处理
（经典的两将军问题）。所以设备必须重试 —— 实测就出现过：服务器已入库并返回 200，
但设备那边 `esp_http_client_fetch_headers()` 判为失败，于是同一条 `failed` 被发了 3 次。

如果不管，一次失败就会留下三条一模一样的「失败」记录，`sample_count` 变成 3，
页面显示成「本次新采集入库 4 条」——**看起来像证据，其实是错的**。

**服务器规则**：同一 `request_id` + 同一终态 `cmd_state` 已存在时，返回
`{"ok":true,"duplicate":true}` 且**不再入库**。判定很窄，只覆盖 `done` / `failed`：

> 终态在状态机里本来就冻结了，第二条不携带任何新信息。
> （与 `/api/poll` 不写 `readings` 是同一个道理：没信息的请求不留痕。）

## 8. 与「三级反馈」的关系

这张图解决的是**一条指令内部**的状态。而人与设备的交互还有另一层：
「本地确认 → 服务器接收 → 查看者回应」三级反馈必须严格分开，
**没有第三级的证据就不能显示「对方已收到」**。那属于第3周的实体求助闭环，见后续文档。

## 9. 已知限制

1. 无离线补发：设备断网期间产生的指令只能等超时，恢复后不会补执行。
2. 无优先级与取消：一条指令一旦受理，只能等它走完或超时。
3. 无鉴权：任何能访问该端口的人都能下发指令，公网暴露前必须加 token。
4. 单设备 FIFO，未设计多设备并发调度的公平性。
5. `sample_count` 统计的是「带该 `request_id` 的记录条数」，包含回执记录本身
   （`received` 一条 + 采样 N 条 + 结论一条 = N+2），不是纯采样条数。
6. 超时阈值写死 30 秒（`ACCEPT_TIMEOUT_S` / `EXEC_TIMEOUT_S`），未做按指令类型区分。
