## 2. 两条方向相反的数据通道

这是最容易混淆的地方，必须分开理解：

### ① 传感数据：板子 → 服务器（板子主动「推」）

| 层 | 采用 |
|---|---|
| 物理/链路 | ESP32-S3 内置 WiFi 2.4 GHz，连到 AP `431` |
| 网络 | 板子 `10.1.41.160`，服务器（PC 有线）`10.1.41.18` |
| 传输 | TCP（HTTP 跑在 TCP 上） |
| 应用 | `HTTP POST /api/data`，body 为 JSON，`Content-Type: application/json` |
| 周期 | `POST_INTERVAL_MS = 1000`（1 Hz） |

板子是**主动方**（HTTP 客户端），服务器是被动方。板子不需要知道服务器在不在 —— 发不出去就超时重试下一轮。

### ② 摄像头画面：服务器 ← 板子（服务器主动「拉」）

板子在 `:81` 上提供 MJPEG 流服务，但**服务器是唯一的上游客户端**。浏览器不看板子，只看服务器的 `/api/camera`，由中继把板子的 1 路流分发成 N 路。详见 [`06-摄像头链路与视频中继.md`](06-摄像头链路与视频中继.md)。

## 3. 为什么这样设计

### 3.1 板端只保持 1 路视频连接

OV2640 是 200 万像素传感器，MVP 阶段跑 QVGA 320×240。**实测每多一路客户端，帧率断崖下跌**：单路 6~7 fps，两路直连就跌到 0.1~0.2 fps —— 因为 ESP32 要把同一帧 JPEG 复制 N 份往 N 个 socket 写，WiFi 上行带宽和 CPU 都不够。

改为服务器中转后，板端恒定 1 路，浏览器数量与板子无关。实测 3 个浏览器并发各 3.2~3.6 fps。

附带的好处：网页不需要知道板子 IP（服务器从上报记录里自动取），以后做远程访问只需映射服务器一个端口。

### 3.2 权威时间放在服务端

板子**没有 RTC**，`device_ms` 只是上电毫秒数，只能用来算间隔。页面显示的是服务端的 `server_ms`。这样即使板子时间错乱，展示的时间仍然是对的。

### 3.3 每条记录都带来源 IP

`src_ip` 是「数据来自一台真实设备，而不是页面里的常量」的直接证据。板子的 WiFi IP `10.1.41.160` 与服务器所在 PC 的 `10.1.41.18` 位于同一局域网但不同主机，无法伪造成本机回环。

### 3.4 服务端零第三方依赖

只用 Python 标准库（`http.server` / `sqlite3` / `json`）实现，拷到任何装了 Python 3 的机器上直接跑，不需要 `pip install`。课程环境（机房 PC、借来的笔记本）部署成本最低。

## 4. 「未更新」判定机制

这是第 1 周的核心验收点：**页面必须能证明数据停了**。

```
板子停止上报
     │
     ▼
/api/latest 返回的 age_seconds = now - server_ms 随时间增长
     │
     ▼  age_seconds > STALE_SECONDS(默认 5.0)
     │
     ▼
stale: true  →  页面数值冻结、保留最后一次的服务器时间、显示「未更新 · 已 N 秒」
```

关键点：**页面不自己倒计时**，而是每轮轮询都看服务器返回的 `age_seconds`。这样页码显示的时间永远与服务端一致，且能同时反映「板子停了」和「服务器停了」两种故障。

## 5. 目录职责划分

| 目录 | 职责 | 是否入库 |
|---|---|---|
| `server/` | 服务端进程：接收、存储、查询、导出、视频中继 | ✅ |
| `web/` | 单文件前端页面，无构建步骤 | ✅ |
| `firmware/esp32_imu/` | 真板子固件（ESP-IDF 5.4.4） | ✅ 源码，`build/` 排除 |
| `learn/step1_imu/` | 最小学习工程：只读 IMU 打串口，用于理解每一步 | ✅ 源码 |
| `sim/` | 板端模拟器，无硬件时的联调替身 | ✅ |
| `tools/` | 数据分析脚本（噪声基线、断流排查） | ✅ |
| `debug_logs/` | 编译/烧录/排错过程的原始日志与抓包 | ✅ 过程证据 |
| `data/` | SQLite 数据库（含真机数据） | ✅ 观测证据 |
| `docs/` | 开发板原理图/手册 | ✅ |

## 6. 单元1 后续两周的架构演进方向

| 周次 | 新增通道 | 新增状态 |
|---|---|---|
| 第 2 周 | Web → 服务器 → 板子 的**下行指令**通道 | 请求状态机：`issued → received → done / timeout`，用 `request_id` 关联 |
| 第 3 周 | 板载实体按键 → 本地反馈（LED/蜂鸣器）+ 远端反馈（Web） | 物理动作与页面状态互证 |

第 2 周的关键点在于：现在的架构只有「板子推」这一条上行通道，板子是纯发布者。要支持远程指令，板子必须变成**双向**的 —— 要么服务器把指令缓存下来等板子来取（长轮询 / 轮询下行队列），要么建立长连接（WebSocket / MQTT）。在只有 `esp_http_client` 的现有固件上，最小改动方案是**板子在每次上报的响应体里捎带下行指令**。
