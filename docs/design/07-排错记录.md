## 1. 芯片型号判定错误（**总根源**）

**现象**：一连串莫名其妙的寄存器异常 —— 量程写了不生效、数据格式对不上、Y 轴冻结。

**定位**：读 `CHIP_ID (0x00)` 得到 **0x90**，而原理图标注的 QMA7981 公开手册是 **0xE7**。进一步探测 6 个 QMA6100P 特有寄存器（0x33/0x45/0x46/0x4A/0x56/0x5F）全部 ACK，5 档量程（含 ±32g）全部被接受。

**根因**：**QMA7981 已 EOL 停产，QMA6100P 是其 pin-to-pin 兼容换代型号**（同封装 LGA-12、同 I²C 地址 0x12、同 14 位 ADC）。乐鑫后续批次换料后**原理图文案未同步**，但 esp-bsp 组件库已改为 `qma6100p`。

**修复**：
- 驱动按 QMA6100P 真实寄存器行为重写
- 新增 `imu_identify()`，上电自动打印完整证据链（换任何一块板都能自证）
- 固件内变量/函数/日志全部从 `QMA7981_*` 改名为 `QMA6100P_*`
- 文件头加「关于芯片型号」专节 + 警告「不要照 QMA7981 手册改」

详见 [`02-硬件与传感器.md`](02-硬件与传感器.md) 第 3 节。

## 2. 量程寄存器 `0x00` 非法

**现象**：按 QMA7981 手册写入 `0x0F = 0x00` 想设 ±2g，但读回不生效，且静止时模长算出来是 **1.5g**（应为 1.0g）。

**根因**：QMA6100P 的量程是**位编码**：`0x01`=±2g、`0x02`=±4g、`0x04`=±8g、`0x08`=±16g、`0x0F`=±32g。**`0x00` 是非法值**。

**修复**：写 `0x0F = 0x01`。带宽同理，合法值是 `0b101`（1024Hz），写 `0x10 = 0x05`。

## 3. Y 轴上电冻结在 -FS

**现象**：上电后 Y 轴读数冻结在负满量程，怎么写寄存器都不动。

**修复**：**软复位** —— 写 `0x36 = 0xB6`，延时 20ms，再写 `0x36 = 0x00`。

事后确认 `0x36` 正是 QMA6100P 的 `SW_RESET` 寄存器，QMA7981 手册里根本没有它 —— 又一条型号勘误的佐证。

**初始化顺序**也必须正确：先 `0x11 = 0xC0` 退出睡眠，再设量程/带宽。

## 4. I²C 扫描零长度读总是失败

**现象**：写了个 I²C 扫描，用零长度读探测设备，结果**全程报 `i2c data read length error`，永远探测不到任何设备**。

**修复**：必须用 **1 字节真实读**：

```c
uint8_t dummy;
esp_err_t err = i2c_master_write_read_device(I2C_PORT, addr, &dummy, 0,
                                             &dummy, 1, pdMS_TO_TICKS(20));
```

## 5. 编译目标成了 esp32 而非 esp32s3

**现象**：`step1_imu` 工程编译通过，但行为全错。查 `sdkconfig` 发现 `CONFIG_IDF_TARGET="esp32"`。

**修复**：手动改 `sdkconfig` 里的芯片目标为 `esp32s3` 并重编。

`idf.py set-target esp32s3` 在当时的操作方式下**没有生效**，最终靠手动改配置文件解决。

## 6. 板子卡在 download 模式

**现象**：固件编译烧录都成功，但板子不运行 app。串口一直输出：

```
rst:0x15 (USB_UART_CHIP_RESET), boot:0x0 (DOWNLOAD(USB/UART0))
waiting for download
```

读串口 0 字节输出。服务器最后一条数据是前一天 15:39，确认板子已停 ~22 小时。

**排查过程**（全部失败）：esptool 硬复位、pyserial RTS 脉冲、DTR 脉冲、烧录后不复位直接读。

期间查清了 USB-JTAG 的控制线映射：**DTR = GPIO0(IO0)，RTS = EN**

| 目的 | 序列 |
|---|---|
| 进下载模式 | `DTR=True`（IO0=0）+ RTS 脉冲 |
| 正常运行（硬复位） | 保持 `DTR=False`，RTS 脉冲：`RTS=True → sleep 0.2 → RTS=False` |

**根因**：**不是复位序列写错，是板子本身卡在 download 模式**（疑似 GPIO0 被拉低 / BOOT 键卡住）。

**修复**：用户拔插 USB 后恢复，`boot:0x2a (SPI_FAST_FLASH_BOOT)`，串口正常出日志。**同一个复位序列随即生效**。

**遗留经验**：
- Windows 上 DTR 的变化**只在设置 RTS 时才传播**
- 排查串口的可靠方法：`run_idf.py -p COM5 monitor` 会打印 ROM 启动行，可直接看 `boot:` 模式
- ⚠️ pyserial 打开 COM 口会拉 DTR/RTS，**等于顺手给板子复位**（诊断时相当于自动做了一次干净基线）

## 7. ESP32-S3 温度传感器量程越界

**现象**：`temperature_sensor_install()` 返回 `ESP_ERR_INVALID_ARG`，日志报 `Out of testing range`。

**根因**：ESP32-S3 只有 **5 个预定义档位**（`components/soc/esp32s3/temperature_sensor_periph.c`），量程必须**完整落在某一个档位内**：

| 档位 | 范围 | 精度 |
|---|---|---|
| 1 | 50 ~ 125 °C | |
| 2 | 20 ~ 100 °C | |
| 3 | **-10 ~ 80 °C** | **±1（最准）** |
| 4 | -30 ~ 50 °C | |
| 5 | -40 ~ 20 °C | |

当时填的是 `-10 ~ 110`，**没有任何档位能覆盖这个区间**，所以失败。

**修复**：改用 `TEMPERATURE_SENSOR_CONFIG_DEFAULT(-10, 80)`，实测读到 44~47 °C。

## 8. `main/CMakeLists.txt` 加 `REQUIRES` 反而编译失败

**现象**：为了用温度传感器，在 `main/CMakeLists.txt` 里加了 `REQUIRES esp_driver_tsens`，结果 `esp_wifi.h` / `esp_timer.h` **全部 not found**，`BUILD_EXIT=2`。

**根因**：ESP-IDF 中组件**不写 `REQUIRES` 时默认纳入所有组件**；一旦显式指定，就**只剩指定的那几个**。

**修复**：**撤掉 `REQUIRES`**。温度头文件本来就在默认依赖里，不需要声明。

## 9. 新旧 I²C 驱动链接期互斥

**现象**：接入摄像头后启动直接 abort：

```
E i2c: CONFLICT! driver_ng is not allowed to be used with this old driver
```

**根因**：IDF 5.x 里新旧 I²C 驱动只要**同时被链进可执行程序**就会冲突，由 `__attribute__((constructor))` 在**链接期**检查（`components/driver/i2c/i2c.c` 的 `check_i2c_driver_conflict()`）—— **跟你实际有没有用新驱动无关**。

**修复**：`CONFIG_SCCB_HARDWARE_I2C_DRIVER_LEGACY=y`，让 camera 组件选 `driver/sccb.c` 而非 `sccb-ng.c`。

## 10. 摄像头抢 I²C 引脚导致 IMU 失效

**现象**：摄像头初始化成功、能出图，但**IMU 读寄存器全部失败**。

**根因**：esp32-camera 自己调 `i2c_driver_install(I2C_NUM_1, GPIO4/5)`，把 GPIO 输出矩阵抢走了。

**修复**：

```c
.pin_sccb_sda  = -1,          /* 不指定引脚 */
.sccb_i2c_port = I2C_NUM_0,   /* 复用 IMU 已装好的总线 */
```

两设备同挂一条总线（IMU=`0x12`、OV2640=`0x30`）互不影响。

## 11. 单线程 httpd 被 MJPEG 堵死

**现象**：网页摄像头区常年显示「未连接」；偶尔刷新后能用一小会儿，再动一下就死。极具迷惑性 —— **第一个人打开正常，他刷新一次或开第二个标签页后就对所有人无响应，只有重新上电才恢复**。

**定位过程**（一条可复用的排查套路）：

1. `diag2.py / diag3.py`：TCP 层能连上 `10.1.41.160:81`，但 `GET /` 超时、`/capture` 第一次成功后续连续超时 → **说明是服务器 CPU/会话层面被堵，不是网络断**
2. `read_serial.py` 抓串口 → 看到 `esp-tls [sock=57] select() timeout`，HTTP POST 往返从 1s 涨到 4~5s
3. 查 IDF 源码 `components/esp_http_server/src/httpd_main.c:334` → **`while(1) httpd_server(hd)` 单线程**，URI handler 同步调用

**根因**：MJPEG 推流 handler 是无限循环，写在单线程 httpd 里会把整个服务器堵死。

**修复**：`httpd_req_async_handler_begin()` 异步化 + 客户端名额 + 防连接泄漏 + 抖动容忍。详见 [`06-摄像头链路与视频中继.md`](06-摄像头链路与视频中继.md) 第 3 节。

**验证方式**：脚本 `verify_cam.py`、`combined_diag.py`（串口 + 网络同步对齐，最能看清问题）。

## 12. 中继断流后永不恢复

**现象**：`/api/camera/status` 显示 `state=error, upstream_running=False, last_frame_age=69秒`，中继已死一分多钟没恢复，但**板子活着**（IMU 1.2 秒前还在上报，ping 0% 丢失）。

**根因**：`_run()` 是一次性的，上游一断线程就退出并置 error。而重启 pump 的路径只有 `subscribe()` —— **如果断流那一刻恰好没有观看者，就再也没人调用 `subscribe`，中继永远停在 error 对外 503**。

**修复**：外层重连环 + **看门狗线程**（每 2 秒检查「有订阅者但 pump 不在」就拉起）+ 卡死检测（连续 12 秒解不出帧判为断流）。

**验证**：`selfheal_test.py` —— 第 2 轮无需重启服务器直接恢复到 2.56 fps。

## 13. `global` 声明位置导致 SyntaxError

**现象**：给服务端加 `MAX_ROWS` 参数后直接启动失败：

```
SyntaxError: name 'MAX_ROWS' is used prior to global declaration
```

**根因**：`main()` 里把 `global MAX_ROWS` 写在了 `ap.add_argument(..., default=MAX_ROWS)` **之后** —— **argparse 的默认值也算「使用」**。

**修复**：把 `global MAX_ROWS, STALE_SECONDS` 提到 `main()` 第一行。

**顺带修了原有 bug**：`--stale` 之前只改局部变量、**实际不生效**（就是同一个原因）。

## 14. 网页「无法连接服务器」

**现象**：页面能打开，但所有 API 请求失败。

**根因**：`index.html` 用相对路径 `/api/*`。当页面被 IDE 以**静态预览**方式打开（端口 60243）时，请求打到了静态服务器上，而不是 8000 端口的 `server.py`。

**修复**：

```javascript
const API_BASE = (location.protocol === 'http:' || location.protocol === 'https:')
  ? location.origin
  : 'http://127.0.0.1:8000';
```

**排查套路**：先看 8000 端口有无进程 → 没有就启 `server.py`；长期用双击 `start_server.bat`。

## 15. 后台任务被杀导致服务静默停止

**现象**：网页突然「无法连接服务器」，但 `server_runN.log` 里**没有任何 traceback**，全是正常的 200 请求记录。

**根因**：用工具的后台任务方式启动 `server.py`，**任务被回收时子进程会一起被杀**。

**判断方法**：看日志末尾**有没有 traceback** —— 没有 = 被外部终止，不是代码崩。

**修复**：重开后台任务；长期自用双击 `start_server.bat`（独立窗口，不受会话影响）。

## 16. `|a| ≈ 0.64g` 虚惊一场

**现象**：`step1_imu` 烧录后串口读出的合加速度只有 **0.64g**，而静止应为 1.0g。

**怀疑**：拼 14 位数据那行 `(msb << 6) | (lsb & 0x3F)` 写法错，按 datasheet 低字节有效位在 bit7~2，应改为 `lsb >> 2`。

**验证**：改成 `lsb >> 2` 重新烧录后 **`|a|` 仍为 0.64**。

**根因**：两处只差最低 6 位（约 0.01g 量级），根本不是主因。经用户确认，**是板子没放平**。

**处理**：`lsb >> 2` 的改动保留（符合 datasheet，正确）。

## 17. 数据断流 18.6%（环境问题，非代码）

**现象**：`tools/gap_check.py` 统计最近 30 分钟：88.6% 的间隔 ≈ 1s，但 **2.4% 为 3~10s、0.6% 超 10s，断流累计占比 18.6%**；板端 `seq` 累计跳过 369 条 → **板子自己没发出去**（不是服务器丢）。

板端串口：`esp-tls select() timeout` → `ESP_ERR_HTTP_CONNECT` / `ESP_ERR_HTTP_EAGAIN`；摄像头 `httpd_sock_err error in send: 11(EAGAIN)/104(ECONNRESET)`。

### 逐项排除

| 检查项 | 实测 | 结论 |
|---|---|---|
| 信号强度 | RSSI **-32 ~ -38 dBm**（极强） | ❌ 排除距离/信号弱 |
| 有线链路 | ping 网关 `10.1.41.254` → **0% 丢包、平均 0ms** | ❌ 排除 PC/路由器有线侧 |
| **最后一跳** | ping 板子 `10.1.41.160` → **33~40% 丢包、平均 ~900ms**（正常应 <5ms） | ✅ **问题定位在无线上行** |
| 摄像头负载 | 用 `--camera-url http://127.0.0.1:9/stream`（不拉板子流）做对照，**断流依旧甚至更差** | ❌ 排除摄像头抢带宽/CPU |
| WiFi 省电 | 加 `esp_wifi_set_ps(WIFI_PS_NONE)` 后重测，仍 40% 丢包 | ❌ 排除 Modem-sleep |

### 结论

剩余可能：2.4G 同信道干扰 / AP 拥塞、板子发射功率弱、**USB 供电不足**（强信号 + 高丢包的典型原因）、USB 3.0 口干扰 2.4G。**属环境问题，靠物理手段改善。**

### 已做的固件改善

- POST 超时 `5000 → 2000` ms（卡住时不拖死主循环 5 秒）
- 新增上报 `rssi` 字段（`esp_wifi_sta_get_ap_info`，失败发 null）
- 服务端 `EXTRA_COLUMNS` 加 `rssi`、INSERT 扩列、CSV 导出加列
- 网页新增「WiFi 信号」卡片（dBm + 很好/尚可/偏弱/很差 四档）

### 新增的诊断工具

| 脚本 | 用途 |
|---|---|
| [`tools/gap_check.py`](../../week1/tools/gap_check.py) | 间隔分布 + 缺口清单 + 断流占比 + seq 跳过量，**判断是板子没发还是网络丢的关键脚本** |
| [`tools/peek_recent.py`](../../week1/tools/peek_recent.py) | 打印最近 N 条原始读数 + 统计 |
| [`tools/analyze_noise.py`](../../week1/tools/analyze_noise.py) | 静态噪声分析（各轴均值/标准差/峰峰值/温度相关系数） |

> 注意：表里没有 `server_time` 列，要用 `server_ms` 换算。

## 18. 其他零星坑

| 坑 | 说明 |
|---|---|
| Bash PATH 被清空 | WorkBuddy 的 shim 脚本导致 `dirname: command not found`，所有外部命令失效。临时逃生：在命令开头显式 `export PATH="...PortableGit.../usr/bin:.../bin:$PATH"`；也可改用 PowerShell 执行 |
| `xtensa-esp-elf-ar.exe: unable to copy ... Permission denied` | 沙箱偶发拦住归档工具写文件，**重跑一次增量编译即可过**（文件本身可写，已验证） |

| PowerShell stdout 捕获不稳 | 需 `Out-File` 落盘后再读 |

| SQLite 删除后文件不变小 | 空间被复用，要真正缩容得 `VACUUM` |
| 时间对不上 | 板子没有 RTC，`ts` 是上电毫秒数；权威时间是服务端的 `server_ms` |
| 5GHz WiFi 连不上 | ESP32 只支持 2.4GHz |
