## 断网实测（第3周当堂验证，2026-09-28 完成）
任务卡两句：「断开外网后本地仍能确认按键已触发」「无远端接收证据不得显示对方已收到」。
- **工具**：`tools/offline_test.py`（只取证不替你下结论）+ `tools/session_check.py`（重启检测）。
- **流程必须三步**：取基线 → 停服务器 → **轮询 max(id) 确认连续 4 秒零新增** → 才请人按键。
  **第三步不能省。** 第一次漏掉它，先取基线再发停服命令就直接问人按，
  而停服要几秒（PowerShell 启动 + 结束进程），那几秒服务器还活着 ——
  日志显示 5 次 `POST /api/help` 全部 201 入库，整轮数据作废。
  这个"基线快照与服务器真正离线之间必然有几秒空隙"是通用陷阱。
- **结果**：静默 71.5 秒、窗口内求助事件 0 条；操作者看到短亮（本地确认）+ 快闪 5 次（没送出去）。
  恢复后板子 0.0 秒接上、**没有补发**（固件对求助是单次尝试、不缓存）。
- 误产生的待回应事件**保留为历史、标记已取消，不删除**。
- **仍未查明**：9/23 那次 4.63 小时断网后板子重启过（device_ms 110.5s→185.9s，
  墙钟过 4.63 小时），原因不明；79 秒短窗口未复现。
- `offline_test.py` 的判据是找**零记录静默段**，不是数"窗口内新增几条" ——
  第一版数条数，把"取完基线到停服之间那 7 秒"的 6 条正常记录判成了
  "消息其实送到了"，得出反向结论。
- `session_check.py` 判据是**隐含开机时刻**（`server_ms - device_ms`）的**持续**偏离。
  踩了三次才定：① 用 seq 变小判重启 → 把第1周数据模拟器（seq=99999）的 68 条也算进去，
  报出 118 处"重启"；② 用"上一条记录的值"当基准 → 板子偶尔把早先构造好的报文
  **迟到送达**（实测 seq 与 device_ms 都小于前后记录），一次迟到就把基准永久推偏，
  8 个会话报成 19 个；③ 滚动中位数 → 只把损害缩到离群值自己那一条。
  最终用"攒够 5 条一致且持续偏离才确认换会话"。

## 网页改版（2026-09-28，两轮）
- 用户要求"优化网页"，选了 **布局与信息层级 / 趋势图 / 深色模式**（**没选移动端**），幅度"保持现有风格精修"。
- **第一轮（精修）** —— 改版前 @1280px 页高 2743px，教学求助占 26.4%、摄像头 19.7%，
  核心实时数据只占 8%，**解释性文字比数据还占地方**。做了：
  色值收成语义变量（深色只需重定义一组）；画布颜色走 `getComputedStyle` + `matchMedia`
  监听；长说明折成 `<details>`（summary 留结论、只折推导过程）；卡片按"回答什么问题"分两组；
  趋势图三档时间窗 + 真实时间轴 + 空档断线 + 纵轴最小跨度 0.25g + 悬停读数（独立画布层）。
- **第二轮（分区标签页）** —— 用户看完说「我看这也没有变化，可以分类，全部都放到一个界面
  是不是太臃肿了」。**两条都对**：
  · "没有变化"是因为我把"精修"理解成只改样式不改结构 —— **用户选"精修"是在答"幅度"，
    不等于他认可现状没问题**；
  · "臃肿"才是病灶：一页塞四件事（实时数据/下发指令/教学求助/摄像头/历史数据）堆到 2400px+。
  → 改成六个分区：**概览 865px（默认）｜交互 400｜求助 820｜影像 482｜数据 604｜全部 2521**。
  分区用 `body[data-tab]` + 纯 CSS 显隐（JS 只改一个属性）；URL hash 直达（验收可直接给 `#help`）。
- 结果（同条件复测，把 git 里旧文件临时放回原位、同源无 CORS、同脚本量三档视口）：
  @1280px 2743→2455（−10.5%）｜@768px 2855→2582｜@390px 4362→3974，整页横向溢出 有→无；
  分区后每个单区都在 400~865px。
- **新增工具**：`tools/shoot.py`（真实 Chrome 截图，支持深色模拟/指定时间窗/hash 直达）、
  `tools/img_sample.py`（**标准库**解 PNG 取像素）、`tools/web_audit.py`（改版审计）。

### 网页这两轮踩的坑（复用价值高）
1. **`/api/history` 是"取最近 N 条"不是"按时间"** → 加时间窗时用 limit，
   实测 `limit=3600` 返回的 3600 条**跨了 4.6 天**（设备有离线空档）。
   界面写着"最近 1 小时"、画的却是 4 天。→ 给接口加 `minutes` 参数按时间过滤。
   **凡"最近 N 分钟"类界面，时间必须由后端按时间过滤，不能靠条数。**
2. **纵轴自动缩放会把噪声放大成"故障"**：静止时噪声仅 ±15mg，自动缩放把它撑满图高。
   加最小跨度修掉。**刻意没用分位数裁极值** —— 本页面盯的是加速度峰值，裁掉尖峰等于藏证据。
3. **横轴按下标均分会伪造数据**：设备离线那段被压成水平直线，看起来像"这段时间一直是这个值"。
   → 按真实时间定位 + 空档处断开曲线。
4. **分区把面板藏起来，会连带藏掉"有人在求助"这个信号** —— 分区的隐藏副作用。
   → 顶部标签加徽标／小圆点。**凡把内容收进标签页，都要问一句"里面有没有需要被看见的警报"。**
5. **`hidden` 属性会被 `display` 盖掉**：UA 的 `[hidden]{display:none}` 优先级低于任何
   带 `display` 的作者样式 → 徽标永久显示 0，在最不该误报的地方挂了永久假警报。
   → 全局加 `[hidden] { display: none !important; }`。
6. **canvas 在隐藏容器里 `clientWidth` 是 0**，`|| 900` 兜底会真按 900px 画一张再被拉伸。
   → 宽度为 0 时跳过绘制，切到可见时强制重画。
7. **两个假通过**：① 审计里"没有 JS 报错"读的是一个从没被写入过的列表，必然通过；
   ② 量隐藏元素的尺寸得到 0，那条"摄像头限高 ≤340px"自动通过。
   还有 ③ 浏览器实测用 JS `.click()`，**对隐藏元素照样生效** → 按钮点不到也算通过。
   → 对策：**每个检查都要有反例**（故意抛错验证探测器；先切分区再量尺寸；先切分区再点）。
8. **目视判断图像不可靠**：CDP 模拟深色后 JS 回读背景色明确是 rgb(25,25,23)，
   我看截图却觉得还是浅色，白花时间查 CSS。采样后平均亮度 36.8 vs 243.3 —— 深色一直是生效的。
9. **shell 会吃掉提交信息里的反引号**（当命令替换执行）→ 提交信息一律写文件
   再用 `git commit -F`，不在 shell 里内联反引号。
10. **测量口径不一致会污染文档**：把"PNG 高度 ÷ 2"当页高写进文档，与另一次口径不同。
    宁可重测也不要拼凑数字。

## 第2周补齐（2026-09-23，实现要点）
- **暂停周期上报**：指令靠搭车在板子**自己上报请求的响应体**里下发 → 上报一停通道就断。
  解法：暂停期间改用 `POST /api/poll` 心跳——**不写 readings，只为取指令**。
  服务端 `COMMAND_TYPES={recollect,pause,resume}` 白名单；`/api/latest` 带出 `paused`
  （否则会把"我们让它别上报"误判成"设备掉线"）。真机：暂停 6 秒 +0 条、心跳仍活、
  期间点采集新增 100% 是 `trigger='command'`、0 条 timer。
- **失败态**：加了**受限故障注入口** `--fault-injection`（默认关）+ `POST /api/debug/fault`
  → 接下来 N 条**指令采集上报**返回 503。**只拦样本(cmd_state 为空)、不拦回执**，
  否则设备唯一的求援信道被切，测试只会变成超时。真机：failed 带 note，库内 0 条样本
  + 1 条失败回执；**撤掉故障后同一块板子能 done**（没有这个对照就排除不了"板子有病"）。
- **固件：采集与结论分两次回报**。样本不带 cmd_state，采完单独发结论(done/failed+note)。
  若结论搭在最后一条样本上，整批被拒时结论永远送不出去 → 只能等 exec 超时，
  于是"设备说失败"与"服务器没听到"混为一谈。
- **重复点击闸门**：`active_for(device_id, ctype)` 查同类在途 → 409 + existing_request_id。
  **按"同类"不按设备全局**（采集在途时点暂停必须放行）；**闸门必须在服务器**
  （界面 disabled 拦不住两个标签页）。网页收到 409 改为**接管那条在途指令继续跟踪**。
- **幂等**：同 request_id + 同终态 cmd_state 已存在 → 返回 `{duplicate:true}` **不再入库**。
  原因：服务器已 200 入库但板子 `fetch_headers` 超时判失败 → 板子重试 → 库内 3 条重复 failed。
  两将军问题：设备必须重试，服务器必须免疫。
- 新增工具：`dup_click_test.py`(并发重复点击，自清理)、`fail_acceptance.py`(失败路径真机)、
  `browser_test_fail.py`(真浏览器验证网页显示失败)。
- **实测发现（未解决）**：板子一次 `POST /api/data` 要 **0.5~2.5 秒**（串口日志可证），
  偶发 `HTTP -1` 请求根本没完成。它解释了此前所有偏大耗时（端到端 4~13s、
  按下→采样 0.4~1.2s）——**不是代码慢，是网络往返慢**。可试 keep-alive（现已每条新建 TCP）。

## 第3周：实体按键与本地反馈（实现要点，复用价值高）
- **硬件必须查、不能猜**（第1周 QMA7981/QMA6100P 的教训）：
  - 4 个用户键**不是 4 个 GPIO**，是挂在同一条 ADC 上的电阻梯：`4-Keys: ADC1_CH0` = **GPIO1**。
    实测电压 UP+ 365~367 / DN- 800~802 / PLAY 1981 / MENU 2409~2414 mV，空闲 3162 mV
    （原理图设计值 380/820/1980/2410，偏差 ≤20 mV）。判读用相邻中点做边界。
  - 本地反馈**只能用 LED**：本板**没有蜂鸣器**、**没有可编程 RGB 灯**，
    唯一软件可控的是绿色 Module Power LED = **GPIO3**，且官方明确要求
    **开漏输出、不得上拉，否则可能烧 LED**。没有蜂鸣器这点最容易想当然。
  - 原理图 PDF 提取文本要用 `pypdf` 的 **`extraction_mode='layout'`** —— 普通模式把
    按键名和电压提取成乱序的，靠列坐标才能正确配对。
- 固件三取舍：① 灯效走**队列 + led_task**（在按键任务里 `vTaskDelay` 闪灯会丢按键）；
  ② 按键采集**放主循环**（HTTP 全工程只有主循环一个使用者，两个任务会争 seq/http_client）；
  ③ 消抖 3 次 + **只在「抬起→按下」边沿触发**（长按不重复）。
- 三种触发在数据层可分：`trigger` = `timer` / `command` / `button`，
  后两者各带 `request_id`（`CMD-…` / `BTN-…`）。
- 新增字段 `press_delay_ms`（按下→首条采样组装完成）。实测 471~1221 ms ——
  它如实暴露"主循环在等 HTTP 时按键要排队"这个架构代价。
- **按键没有下行通道**，所以网页上给它画"四阶段时间线"就是伪造证据 —— 面板只列真实发生的。
- 服务器新增 `GET /api/buttons`（按 request_id 聚合成"一次按键一条"）。

## 第3周踩的两个坑（复用价值最高）
1. **设备生成的事件 id 必须跨重启唯一**。第一版用内存计数器 `BTN-MENU-0001`，
   板子一重启归零 → 两次按键同一个 id → 服务器按 id 聚合时**误合并成一条**
   （样本数 10、跨度 105 秒）。修复：加上电随机前缀 `BTN-<6位hex>-MENU-0001`。
   → **注意：这类 bug 产出的是"看起来对的错误证据"，比没有数据更危险。**
   网页已加防线：跨度 >30 秒自动标红「事件 id 可能撞车」。
   旧事件保留在库里当样本，没有清理。
2. **串口工具自己会把 ESP32-S3 复位**。pyserial 打开串口时默认拉高 DTR/RTS，
   这两个信号的组合会触发芯片复位 → USB 重新枚举 → Windows 下**旧句柄静默失效**
   （不报错，只是再也读不到数据），表现为"200 秒采集一个字节都没有"，
   但板子其实活得好好的（服务器一直在收数据）。
   修复：打开后 `setDTR(False)`/`setRTS(False)`，并加"5 秒无数据就重开"的看门狗。
   → 教训：**调试工具本身也会改变被测对象；"观测不到"要先怀疑观测手段。**
- VPS部署：课程明确要求，等于把 server.py 上公网、板子 SERVER_URL 改公网地址、摄像头改板子主动推流。

## 第2周：下行指令与回执状态机（实现要点，复用价值高）
- 文件：`week1/server/commands.py`(状态机/新)、`server.py`(路由+捎带)、`main.c`(解析+执行)、
  `web/index.html`(面板)，工具 `tools/cmd_selftest.py`(模拟板子)、`cmd_acceptance.py`(真机)、`check_web.py`。
- **核心取舍：指令不推送，搭车下发**。板子只 POST 不监听端口 → 把待执行指令塞进
  `/api/data` 的**响应体**里，板子下次上报时顺手收下。不给板子开端口、不引入 MQTT/WebSocket。
  代价=送达延迟 ≤1s（等下一次 1Hz 上报）。若将来要秒级以下实时控制才值得换长连接。
- 状态机：`issued → delivered → received → done`，**只进不退**（网络抖动会重复上报）；
  终态冻结。超时由**后台线程每秒扫并主动落库**（不是查询时顺手算，否则超时无服务器侧证据）。
- **超时分两段并记 `timeout_stage`**：`accept`=板子没来取（掉线/重启）；`exec`=取了没执行完。两种故障完全不同。
- **区分「刷新」与「新采集」靠数据字段，不靠时间猜**：readings 表加
  `request_id`(TEXT，定时上报为 NULL) + `trigger`('timer'|'command') + `cmd_state`('received'|'done')。
- 固件侧要点：`esp_http_client_perform()` **会丢掉响应体**，必须改
  `open→write→fetch_headers→read→close`；解析用 IDF 自带 `cJSON`（组件 json 默认在构建里，
  **不要写 REQUIRES**）。采样逻辑抽成 `build_payload()` 供两种触发方式复用。
- 接口：`POST /api/command`(202 返回 request_id)、`GET /api/command/<id>`、`GET /api/commands`。
  参数服务端限幅 samples∈[1,100] interval∈[20,1000]，固件再挡一层。
- **真机实测**（CMD-20260918-0005，12 条/100ms）：受理→下发 893ms（等 1Hz 上报）、
  下发→接收 426ms（一次 HTTP 往返）、接收→完成 2785ms、**端到端 4104ms**；
  13 条记录带同一 request_id，`trigger=command`，模长 0.99~1.01g。
- 超时实测：CMD-20260918-0004 在 `accept` 阶段 30.45s 后判定 timeout。
- **排查教训（又踩一次）**：`global X` 必须写在**任何对 X 的使用之前** —— argparse 的
  `default=X` 也算使用，写在后面直接 SyntaxError。（第1周 server.py 的 MAX_ROWS 同样问题）
- 已知限制：无离线补发、无优先级/取消、无鉴权、单设备 FIFO。

## 传感器静态噪声基线（2026-09-14 实测，600 条 / 13.5 分钟，板子静止）
- 工具：`tools/analyze_noise.py [样本数] [设备名]`，输出各轴均值/标准差/峰峰值 + 温度相关系数。
- 实测：**ax sd 15.2mg、ay 7.2mg、az 6.3mg、|a| sd 6.3mg**；峰峰值约 60mg（0.06g）。
- **|a| 均值 1.0030 g**（静止应为 1.0g，偏差 0.3%）→ 传感器与 CAL_* 标定均正常。判读：|a| 长期均值≈1.0 就说明没坏。
- 芯片温度均值 52.7°C，但**13 分钟内波动 13°C**（44.3~57.3），TSENS 读数噪声不小，别当精密温度计。
- **温度与加速度相关系数 ≈ 0.02（-0.02~+0.05）→ 无关**。即短时抖动**不是**温度漂移，主因是 MEMS 本底噪声 + 环境微振动 + 供电纹波。
- 结论（答疑用）：静止 ≠ 读数恒定。网页 3 位小数看到跳动是正常物理噪声，不是 bug。想让显示"稳"可降显示位数或加滑动平均（会牺牲响应速度）。

## 关键坑（已踩）
- ESP-IDF 自带 httpd 单线程，视频流死循环会卡死 81 端口 → 已改异步+中继。
- 抗抖动固件已编译但未烧录（COM5 偶现不在系统，需 USB 数据线插回）。
- ⚠️ **Edit 工具偶发"报成功但没落盘"**（2026-09-23 一次会话内至少 4 次）：
  表现是返回 `edited successfully`，但文件里没有那段代码 → 运行时报
  `AttributeError`，或更隐蔽的 `sqlite3.OperationalError: table readings has no column
  named cmd_note`（后者让板子所有上报返回 500、数据断流，而接口自查却"看起来正常"）。
  **对策：一次只发一个 Edit；改完立刻 grep/读取核对；批量改名用脚本 + `assert count==1`
  一次做完再验证。** 并行发多个 Edit 时尤其容易丢。
- **同一模式的第三个坑**：这类 bug 的产物都是"看起来对的错误证据"——
  ①按键事件 id 跨重启重复 → 两条事件被聚合误合并；
  ②重复终态回执未幂等 → 3 条一样的 failed，`sample_count` 虚高；
  ③Edit 静默失败 → 自查脚本检查的是它以为的代码。
  **共同点：重复/冲突/缺失的标识符被当成了新事实。遇到"证据"先问一句"它凭什么只出现一次"。**
