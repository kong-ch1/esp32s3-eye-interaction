## 网页视觉改版（用户要求「优化网页」）

先量化再动手。用真实 Chrome 在 1280px 下量各区块高度，发现两处明显不合理：
**解释性文字占掉的面板比数据还大**（教学求助 26.4%、摄像头 19.7%），
而**核心实时数据只占 8%**。整页 2743px。

用户选了三个方向（多选）：布局与信息层级、趋势图改进、深色模式与视觉精修；
幅度选「保持现有风格精修」。**没有选移动端适配**（但也不能弄坏）。

### 做了什么

1. **设计令牌化** —— 原来散着二十多个写死的色值（同一个"浅灰底"在 6 处各写一遍），
   这种写法没法加深色模式。收成 `--surface-2` / `--ok-fg` / `--s-ax` 等语义变量，
   深色只需重定义一组值。`color-scheme: light dark` 让原生控件跟着走。
   画布颜色走 `getComputedStyle` + `matchMedia` 监听（canvas 不认 CSS 变量）。
   批量替换用脚本并**断言每条命中次数**，真的拦住了两次写错模式的替换。

2. **信息层级** —— 两处长说明折成 `<details>`（summary 留结论、只折推导过程）。
   顺手修一个真问题：`#cmdHint` 既当静态说明又当实时状态，JS 一下发指令就把说明
   覆盖掉了 → 那段说明只能看一次。7 张卡片按"回答什么问题"分成两组。

3. **趋势图** —— 时间窗（1/10/60 分钟）、横轴按真实时间定位 + 空档断线、
   纵轴最小跨度 0.25g、悬停读数（独立画布层）。

4. 其他：摄像头限高 340px、求助列表默认 3 条、表格横向溢出收进容器、
   补 `:focus-visible`、修 `colspan="9"`（表格是 10 列）。

### 结果（同条件复测）

    @1280px  2743 → 2455px (−10.5%)
    @768px   2855 → 2582px (−9.6%)
    @390px   4362 → 3974px (−8.9%)，整页横向溢出 有 → 无
    深色模式 无 → 跟随系统

审计（`tools/web_audit.py`）全绿；原有两个浏览器实测（采集四阶段、求助三级反馈）重跑通过。

### 踩到并修掉的坑

1. **`/api/history` 是"取最近 N 条"不是"按时间"** —— 加时间窗时直接用了 limit，
   实测 `limit=3600` 返回的 3600 条**跨了 4.6 天**（设备有离线空档）。
   那样界面写着"最近 1 小时"、画的却是 4 天。→ 给接口加 `minutes` 参数，
   时间范围由服务器按时间过滤，limit 只当安全上限（上限同时 500 → 4200）。

2. **纵轴自动缩放把噪声放大成"故障"** —— 板子静止时噪声只有约 ±15mg，
   原来的自动缩放会把它撑满整个图高，看着像剧烈抖动。加了 0.25g 最小跨度。
   **刻意没用分位数裁极值**：本页面盯的正是加速度峰值，裁掉尖峰等于藏证据。

3. **横轴按下标均分会伪造数据** —— 设备离线那段会被压成一条水平直线，
   看起来像"这段时间一直是这个值"，而事实是这段时间根本没有数据。
   改成按真实时间定位 + 空档处断开曲线。

4. **审计里的"没有 JS 报错"是个假通过** —— 它读的是一个**从没被写入过的列表**，
   所以必然通过。**一个永远为真的检查等于没有检查。** 改成加载前注入错误监听，
   并**先故意抛一个错验证探测器本身有效**再清空重测（照搬第 2 周失败态验证的对照思路）。

5. **目视判断图像不可靠** —— CDP 模拟深色后 JS 回读背景色明确是 `rgb(25,25,23)`，
   但我看截图觉得还是浅色，白花时间去找 CSS 的问题。写了 `tools/img_sample.py`
   （标准库解 PNG）采样：平均亮度 36.8 vs 243.3 —— **深色一直是生效的**。
   以后"看着像"的结论都先用它验一遍。

6. **测量口径不一致会污染文档** —— 中途把一次"PNG 高度 ÷ 2"当页高写进文档，
   和另一次测量的口径不同。改用**同条件复测**：把 git 里的旧文件临时放回原位
   （同源、无 CORS），同一脚本量三档视口，测完还原并核对 md5。

### 分区带出的三个连带问题（都必须处理，否则是"改好了又改坏"）

1. **canvas 在隐藏分区里 `clientWidth` 是 0**：原来的 `|| 900` 兜底会真按 900px
   画一张（还每秒重画），切回来被拉伸变形。→ 宽度为 0 时直接跳过，切到可见时强制重画。
2. **藏起来的面板会丢掉"有人在求助"这个信号**：这是最危险的副作用 ——
   第 3 周做的整件事靠的就是"看得见"。→ 顶部标签加徽标（有待回应求助时显示数字），
   指令在途时「交互」点小圆点。
3. **测试变成假通过**：两个浏览器实测都用 JS `.click()`，而它**对隐藏元素照样生效** ——
   按钮点不到，测试也"通过"。→ 改成"先切分区 + 断言元素可见"，不可见直接判测试无效。

### 顺带发现一个真 bug：求助徽标永久显示 0

**`hidden` 属性被我自己写的 `display: inline-flex` 盖掉了** ——
UA 样式的 `[hidden]{display:none}` 优先级**低于**任何带 `display` 的作者样式。
结果徽标永久显示"0"，在一个最不该误报的地方挂了永久假警报。
→ 全局加 `[hidden] { display: none !important; }`。

发现它的过程也值得记：审计原本只测"造一条求助后徽标会不会亮"，
而"永远亮着"**同样能通过**那个检查 → 现在两个状态都测。

### 测试自身也错过一次

徽标检查一开始用 `selftest-sim` 当设备名，而页面按**当前设备**过滤求助事件
（这是刻意的安全设计，防模拟数据冒充真机证据）→ 事件被正确过滤、徽标不亮，
看着像功能坏了。**是测试写错了，不是代码错了。** 改成用真机设备名 + `simulated` 标记。

### 又踩一次 shell 的坑

→ **提交信息一律写文件再 `git commit -F`，绝不在 shell 里内联反引号。**

### 第一次测试作废 —— 而且是我流程的错

日志：`10:40:19 / :25 / :28 / :40 / :47` 五次 `POST /api/help` **全部 201 入库**，
服务器最后一条在 10:40:49。也就是说**按键发生在服务器仍存活期间**，
那几次板子收到的是"成功"，灯该是连闪 2 次而不是快闪 5 次。

根因：我的流程是「取基线 → 发停服命令 → 直接问人按」。
而**停服要几秒**（PowerShell 启动 + 结束进程），这几秒服务器还活着，
按键就落在窗口外面了。**基线快照与服务器真正离线之间必然有一段空隙** ——
这是个通用陷阱，任何"停服务前后取证"的测试都会踩。

那 5 条误产生的待回应事件保留为历史、标记已取消（不删除）。

### 第二次改流程，一次干净

改成三步：取基线 → 停服务器 → **轮询 max(id)，等连续 4 秒零新增之后才请人按键**。
第三步把"服务器到底停了没"从**推断**变成**测量**。

结果：静默 71.5 秒、**窗口内求助事件 0 条**（不只是静默段内）；
操作者看到 **绿灯短亮一下 + 快闪 5 次** —— 本地确认成立、且明确告知没送出去。
恢复后板子 0.0 秒接上，**没有补发**迟到的求助。

两句都成立：① 断网后本地仍确认；② 无远端证据就不显示"对方已收到"。
