3. 新建 `main/camera_stream.c/.h`：摄像头初始化 + esp_http_server MJPEG 流（81 端口，/stream 与 /capture），main.c 里 `camera_stream_start()` 在 WiFi 连上后调用，失败只告警不阻断 IMU 上报

### 引脚（esp-bsp bsp/esp32_s3_eye 官方定义，已实测可用）
XCLK15 PCLK13 VSYNC6 HREF7 D0..D7=11,9,8,10,12,18,17,16；SCCB 与 IMU 共用 GPIO4/5

### 两个致命坑（务必记住）
1. **链接期新旧 I2C 驱动互斥**：`E i2c: CONFLICT! driver_ng is not allowed to be used with this old driver` → abort。这是 __attribute__((constructor)) 做的链接检查，`components/driver/i2c/i2c.c` 里 `check_i2c_driver_conflict()`，由 `CONFIG_I2C_SKIP_LEGACY_CONFLICT_CHECK` 控制。
   - 解法：`CONFIG_SCCB_HARDWARE_I2C_DRIVER_LEGACY=y`，让 camera CMake 选 `driver/sccb.c` 而非 `sccb-ng.c`
2. **同组引脚被两套旧 I2C 驱动抢**：camera 自己 `i2c_driver_install(I2C_NUM_1, GPIO4/5)` 后，IMU 读寄存器全失败（GPIO 输出矩阵被后装的抢走）
   - 解法：`.pin_sccb_sda = -1` + `.sccb_i2c_port = I2C_NUM_0`，让摄像头复用 IMU 已装好的总线（IMU=0x12、OV2640=0x30 共存）

## 摄像头「有时能用、大多未连接」根因定位与修复（下午）

### 症状
网页摄像头区常年显示「未连接」；偶尔刷新后能用一小会儿，再动一下就死；IMU 有时显示「未更新」。

### 诊断链路（可复用的排查套路）
1. `D:\aijiaohu\week1\diag2.py / diag3.py`：TCP 层 → `10.1.41.160:81` 能连上，但 `GET /` 超时、`/capture` 第一次成功后续连续超时 → 服务器 CPU/会话层面被堵，不是网络断
2. `read_serial.py`（须用 IDF 那个 python，它自带 pyserial）抓串口 → 看到 `esp-tls [sock=57] select() timeout`、HTTP POST 往返从 1s 涨到 4~5s
3. 查 IDF 源码 `components/esp_http_server/src/httpd_main.c:334` → **`while(1) httpd_server(hd)` 单线程**，URI handler 同步调用

### ★ 根因
MJPEG 推流 handler 是无限循环，写在单线程 httpd 里会把整个服务器堵死：没人 accept 新连接、`/capture` 也无人应答。
后果极具迷惑性：第一个人打开网页正常 → 刷新一次或开第二个标签（旧的 /stream 连接还在）→ 从此 81 端口对所有人无响应 → 只有重新上电才恢复。这正是「有时能用」。

### 修复（camera_stream.c 已改）
1. **异步 handler**：`httpd_req_async_handler_begin()` 拿副本后立即返回，推流交给独立 FreeRTOS 任务（8192 栈，prio 6，绑核 1），httpd 主线程回到 select 循环
2. **客户端名额**：mutex 保护计数，上限 2（`CAM_MAX_STREAM_CLIENTS`），超限返回 503 快速失败而不是挂起
3. **防连接泄漏**：`lru_purge_enable=true`、`recv/send_wait_timeout=2`、`SO_KEEPALIVE` + `TCP_KEEPIDLE=15/KEEPINTVL=5/KEEPCNT=3`、`TCP_NODELAY`（关 Nagle，否则分三次小写入被攒包导致画面卡）
4. **抖动容忍（第二轮补）**：区分 errno。`EAGAIN/EWOULDBLOCK`（对方窗口满/WiFi 一时堵）→ 丢帧继续，连续 8 次才认输（`CAM_EAGAIN_TOLERANCE`）；`104 ECONNRESET`/`128 ENOTCONN` → 立即收摊。
   之前一遇超时就退出推流，导致「客户端不停重连却一直没画面」的死循环
5. 新增 `/ping` 心跳（返回 uptime/clients/heap）、`/` 板端自带预览页（用于区分是网页问题还是板子问题）

### sdkconfig 改动
`CONFIG_LWIP_MAX_SOCKETS` 10→16；新增 `CONFIG_LWIP_TCP_KEEPALIVE=y` + KEEPIDLE/KEEPINTVL/KEEPCNT

### 网页改动（web/index.html）
- 重连必须带 `?nocache=Date.now()`，否则浏览器缓存住上次的失败状态
- 失败退避重试（2s 递增到 10s，20 次后提示重新上电）
- 每 3 秒 `/ping` 心跳：两次失败 → 判死自动重建；`clients=0` 但自己以为还在看 → 判定画面已冻结，同样重建
- 加「重连」按钮

### 实测结论
- 异步改造有效：连续 5 轮「建立→拉 4 秒→断开」，断开后 `/ping` 都能在 0.1~0.3 秒回应，`/capture` 正常返回（改造前第 2 轮必死）
- **单客户端 4~5 fps；两路并发会崩到 0.1~0.2 fps** → 板子扛不住多路，上限设 2 已经是上限
- 注意：pyserial 打开 COM 会拉 DTR/RTS，等于顺手给板子复位（诊断时相当于自动做干净基线）

### 遗留
11:04 之后 COM5 消失、ping 提示主机不可达 → 板子 USB 掉了/断电，待重新插好后烧录含抖动容忍的新固件并复测

### 踩坑
- `xtensa-esp-elf-ar.exe: unable to copy ... Permission denied`：沙箱偶发拦住归档工具写文件，**重跑一次增量编译即可过**（文件本身可写，已验证 CAN_WRITE=YES）
- Python 源码里 `b"<汉字>"` 非法（bytes 字面量只能含 ASCII），用 pyserial/IDF python 时注意
- Verify 脚本 finals: `verify_cam.py`、`combined_diag.py`（串口+网络同步对齐，最能看清问题）；已全部归入 `week1/debug_logs/`

## 摄像头改为服务器中转（用户要求：以后要拿出去远程访问）

### 新增 `server/camera_relay.py`
MJPEG 中继：**服务器与板子恒定只保持 1 路连接**，解析 multipart 取出 JPEG 帧，再分发给任意多个浏览器。
- `CameraRelay(latest_ip_fn=...)`：板子 IP 由 server.py 注入的回调从 `readings.src_ip` 最新一条取，
  **换路由器导致 IP 变了不用改代码**；也可用 `--camera-url` 写死
- 没人观看超过 5 秒自动断开上游；下游队列 `maxsize=2`，满了丢旧帧保最新，避免慢客户端累积延迟
- 上游断开时向所有订阅者投哨兵 `None`，让 `<img>` 触发 onerror → 页面自动重连
- 关键教训：**不要写成 `from server import ...` 反向导入**（循环依赖 + sys.path 问题），改成注入回调

### server.py 改动
新增 `/api/camera`（multipart/x-mixed-replace）与 `/api/camera/status`；`import queue`；
模块同目录导入靠 `sys.path.insert(0, dirname(__file__))`

### web/index.html
`CAM_MODE='server'|'direct'`，默认 server；`CAM_STREAM`/`CAM_HEARTBEAT` 随之切换；
心跳解析改成兼容两种模式（server 读 JSON 的 state/last_frame_age，direct 仍读板端 clients=N）

### 实测
单客户端 6.9 fps；**3 个客户端并发各 3.2~3.6 fps，而板端始终只有 1 路**（改造前 2 路就崩到 0.1 fps）

### 待办 / 遗留
- 含 EAGAIN 抖动容忍的固件**已编译但未烧录**：COM5 一直不在（系统只剩 COM1/COM2），
  但板子 WiFi 在线说明有外部供电。要烧需先让 USB 数据口恢复
- 服务器进程是会话级后台任务，会话结束会被回收；长时间用请双击 `start_server.bat`
- `Start-Process` 在沙箱里拿不到 PID（起不来），起服务要用 `run_in_background` 的后台任务

## 中继自愈修复（11:30 后）

### 现象
用户问"摄像头现在是不是走服务器"时复查：`/api/camera/status` 显示
`state=error, upstream_running=False, last_frame_age=69秒, error='读取中断: timed out'`
——中继已经死了一分多钟没恢复，但板子活着（IMU 1.2 秒前还在上报，ping 0% 丢失）。

### ★ 根因
`camera_relay.py` 的 `_run()` 是一次性的：上游一断（板子重启 / WiFi 抖动掐断 TCP）线程就退出并置 error。
而重启 pump 的路径只有 `subscribe()` —— **如果断流那一刻恰好没有观看者，就再也没有人调用 subscribe，
中继会永远停在 error 对外 503**，表现为"摄像头彻底坏了、刷新也没用"。

### 修复（camera_relay.py）
1. `_run()` 改成外层重连环：`_connect_and_stream()` 返回结束原因，非 "no_viewers" 就退避重连（1.6 倍递增，上限 6 秒）
2. **看门狗线程** `_watchdog_loop()`：每 2 秒检查，只要"还有订阅者但 pump 线程不在"就拉起 —— 这是根治的那一条
3. **卡死检测**：流还连着但连续 12 秒解不出帧 → 判定断流，主动重建（靠 TCP 超时可能几十秒才报错）
4. urlopen 超时 10→8 秒；status 新增 `reconnects`、`state_since` 字段，便于区分"偶发抖动"和"板子在反复重启"
5. `server.py` 的 `api_camera` 首帧等待 8→15 秒（板子重启后要先连 WiFi 再起摄像头，8 秒不够会导致"重连→没帧→再重连"的循环）

### 实测（selfheal_test.py）
- 第 1 轮 13.6s / 26 帧 ≈ 1.92 fps；断开 8 秒后自动 idle；**第 2 轮无需重启服务器直接恢复到 2.56 fps**
- 板子 25 秒内 seq 无回跳（没重启），但上报间隔偶尔到 5~7 秒 → 这解释了网页偶发的"未更新"，是 WiFi 被视频流挤占所致

### 排查技巧
判断"到底是板子死了还是中转死了"三连：ping 板子 → /api/latest 看 age → /api/camera/status 看 state/upstream_running。
三者组合能一次定位，比直接刷网页快得多。脚本：`debug_logs/perf_check.py`、`stability.py`、`selfheal_test.py`
