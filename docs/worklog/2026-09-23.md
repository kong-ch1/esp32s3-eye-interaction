## 补齐 #31：暂停周期上报（已完成并真机验收）

### 实现
- **服务端**：新增 `POST /api/poll`（心跳，**不写 readings**，只为取指令）；
  `COMMAND_TYPES = {recollect, pause, resume}` 白名单，拼错当场 400 并回可用类型；
  `DEVICE_STATE` 内存字典记录每台设备的 `paused / last_seen_ms / last_kind`；
  `/api/latest` 与 `/api/devices` 带出 paused，**避免把"我们让它别上报"误判成"设备掉线"**。
- **固件**：`SERVER_URL` 拆成 `SERVER_BASE` + `PATH_DATA`/`PATH_POLL`；
  `http_post_json(path, …)` 收路径；新增 `s_paused`、`dispatch_command()`、`poll_tick()`；
  控制指令的回执分两次发（received → done），保持四阶段证据链与采集指令一致。
- **网页**：命令面板加「暂停/恢复周期上报」按钮 + 模式徽标；
  `issueCommand()` 统一采集与控制两类指令；三态分开显示（暂停中 / 正在恢复 / 真未更新）。

### 真机验收（2026-09-23，`tools/pause_acceptance.py`，全自动）
```
[1] 基线        3 秒内 +2 条（周期上报正常）
[2] pause 指令  done，四段耗时 980 / 1281 / 610 ms，端到端 2871 ms
[3] 暂停生效    6 秒内 +0 条；paused=True，0.73 秒前刚发心跳 → 命令通道保持
[4] 暂停中点采集 done，新采集 7 条，端到端 4281 ms
[5] 关键断言    7 条新增 100% 是 trigger='command'，**0 条 timer**
[6] resume      done，3 秒内恢复 +2 条
结论 ✓ 「暂停周期上报 + 保持命令通道」成立，且暂停期间的新记录可证明全部来自指令
```
这条证据比原来页面上"比数字"硬得多：周期上报停掉之后，
**库里任何新增记录只可能来自指令**，不可能是页面翻出来的旧值。

### 顺带修的一个 UI 隐患
暂停期间 readings 不再增长，`age_seconds` 必然变大。原来的逻辑只看 age，
会把暂停显示成「未更新 · 已 N 秒」—— 那是冤假错案，而且掩盖了"暂停生效"这个事实。
现在三态分开：暂停中（心跳 N 秒前）/ 正在恢复 / 真未更新。

## 补齐 #32：失败态真实路径 + 重复点击测试（已完成并真机/真浏览器验收）

### 1. 失败态从死代码变成可复现路径
真实环境很难复现失败：拔网线设备连"我失败了"都报不上去；弄挂服务器整条链路一起断。
所以给服务器加了**受限故障注入口**（`--fault-injection`，默认关闭）：
`POST /api/debug/fault {mode:command_data, times:N}` → 接下来 N 条**指令采集上报**返回 503。
**关键：只拦样本(cmd_state 为空)、不拦回执** —— 否则设备唯一的求援信道也被切了，
测试会变成永远超时，反而验不了 failed。启动横幅会明确打印"⚠️ 故障注入已开启"。

固件侧：**采集与结论分成两次独立回报**。样本不带 cmd_state，采完单独发一条结论
（done/failed + cmd_note）。理由：若结论搭在最后一条样本上，整批被拒时结论永远送不出去，
服务器只能等到 exec 超时 —— 于是"设备明确说失败"和"服务器什么都没听到"混成同一件事。

真机实测（CMD-20260923-0008，samples=6）：issued(0.0s)→delivered(0.8s)→received(2.4s)→
**failed(11.1s)**，note="6 条全部上报失败（网络或服务器不可达）"；
库内该 request_id 只有 2 条（1 received + 1 failed），**样本 0 条**；timeout_ms=None。
**对照实验**：撤掉故障重采 → CMD-20260923-0009 done，6 条，10587 ms。
没有这个对照就排除不了"板子本来就有病"。

### 2. 发现的真 bug：重复的终态回执
第一次真机验证时库里出现 **3 条一模一样的 failed**（seq 60/61/62）。根因：
服务器已入库并返回 200，但板子 `esp_http_client_fetch_headers()` 超时判失败
（串口日志 `上报失败 HTTP -1`），于是按设计**重试**结论 —— 服务器每次都又插一条。
**上报是"发出去"和"收到回应"两件事，中间断了设备分不清服务器处理没处理（两将军问题）。
所以设备必须重试，而服务器必须对重试免疫。**
修法：同 request_id + 同终态 cmd_state 已存在 → 返回 `{duplicate:true}` 且**不再入库**
（终态已冻结，第二条不携带新信息；与 /api/poll 不写 readings 同理）。
→ 这是本项目**第二次**被"重复标识符被当成新事实"坑到（第一次是按键事件 id 跨重启重复）。

### 3. 重复点击闸门
`POST /api/command` 先查"该设备是否还有**同类**未走完的指令"，有就 409 并带上那条的
request_id。**按同类判定不按设备全局** —— 采集在途时点暂停必须放行。
**闸门必须在服务器**：界面 disabled 拦不住两个标签页同时点。
网页收到 409 不弹红字，而是**直接接到那条在途指令上继续跟踪**（用户在意的是"我这一下生效没有"）。
实测：5 个并发请求 → 恰好 1×202 + 4×409，且 4 条都指向同一条；库里在途恰好 1 条。

### 4. 两处措辞/统计修正
- 时间线第 4 步「执行完成」→「**执行结果**」：失败时会显示成
  「执行完成 · 执行失败（设备回报）」，自相矛盾。同步改了 4 个测试脚本里的标签。
- `to_public()` 的 `total_ms` 原先只算 done/timeout，**failed 没有总耗时**，看着像半条记录。

### 5. 板子侧 HTTP 往返偏慢（实测发现，未解决）
从板子串口日志看，一次 `POST /api/data` 要 **0.5~2.5 秒**，同一批指令里逐条波动；
期间还有一次 `HTTP -1`（请求根本没完成、服务端没收到）。
它解释了此前所有偏大的耗时（端到端 4~13 秒、按下→采样 0.4~1.2 秒）——
**不是代码算得慢，是网络往返慢**。可能方向：给 esp_http_client 开 keep-alive
（现在每条都新建 TCP，每次重新握手）。需单独验证，本轮没动。
