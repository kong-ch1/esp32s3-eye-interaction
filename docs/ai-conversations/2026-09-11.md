## 三条路，怎么选

**方案 A · 内网穿透（我推荐这个）**
在你电脑上装个隧道客户端（cloudflared 或 cpolar），它会给你一个**公网网址**，外部请求顺着隧道打回你本机的 8000 端口。
- 优点：**免费、server.py 一行不改、域名固定**（Cloudflare Tunnel 用你自己的域名，永远不会变）
- 缺点：电脑必须开机；免费隧道到国内有时延
- 落地量：改固件 `SERVER_URL` 一个宏 + 装个客户端

**方案 B · 云服务器**
把 `server.py` 整个搬到云主机上（有公网 IP），板子直接往云上发，你的电脑变成"访问者"随时看。
- 优点：最正规、最稳，电脑关机数据照样收 —— 顺便把 README 里那句"VPS 部署待补"补上了
- 缺点：要花钱，最低配大概二三十块一个月

**方案 C · MQTT 公有云（IoT 正统做法）**
板子往云端 broker 发布主题，电脑订阅。天生支持异地、断线重连、多设备。
- 优点：EMQX 有免费额度，这才是物联网的标准答案
- 缺点：固件要从 HTTP 改成 MQTT，改动最大（但也就几十行）

## 三个必须提前知道的坑

**① 真正的难点在板子，不在服务器。**
固件里 WiFi 是写死的 `"431"`——**板子挪到没有这个 WiFi 的地方，它根本上不了网**，服务器侧再怎么折腾都没用。解决有三招：把目标 WiFi 的账号密码刷成一样的；固件里配多个 AP 自动切换；或者做配网（板子开机变热点，手机连上去填 WiFi）。

**② 一旦暴露到公网，伪造数据就从"理论风险"变成"现实风险"。**
之前聊过：现在服务端只是如实抄下 `src_ip`，谁都能 POST 一条假的冒充你的设备。**上公网之前必须先加 token 校验**，否则"数据来自本组设备"这个断言在互联网面前一秒破功。

**③ `10.1.41.18` 可能会变。**
宿舍/校园网一般是 DHCP，重启路由器或租约到期 IP 就换了，板子会突然掉线。建议在路由器里给电脑做 MAC 绑定，或者干脆给电脑设静态 IP。

## 为什么显示"未连接"

ESP-IDF 自带的 HTTP 服务器是**单线程**的，源码里就一句 `while(1) httpd_server(hd)`（`esp_http_server/src/httpd_main.c:334`），所有 URI 处理函数都在这个唯一的线程里同步执行。

而 MJPEG 推流的处理函数天然是个**永不返回的死循环**——客户端不断开就一直推帧。于是：

1. 你第一次打开网页，画面正常（这时线程正在给你推流）
2. 你刷新页面或开了第二个标签页，旧的那条连接还占着线程
3. 从此 81 端口**对所有人无响应**：没人 accept 新连接，`/capture` 也没人应答
4. 只有拔电源重插才能恢复

这完美解释了"有时候能用、大多是未连接"。实测证据：`GET /` 直接超时（连 404 都没拿到）、`/capture` 第一次成功 5788 字节耗时 6.46 秒、之后连续 5 次全部超时。

## 为什么"未更新"

同一块板子上 WiFi 被挤占时，IMU 的 HTTP 上报往返会从 1 秒涨到 4~5 秒（串口日志里能看到 `Connection timed out before data was ready`），超过服务器的 stale 阈值就提示"未更新"了。

## 改动

**固件 `main/camera_stream.c`**：推流改成异步 —— 处理函数拿到请求副本后立刻返回，推流丢给独立任务；加了客户端名额上限（最多 2 路）、`SO_KEEPALIVE` + `TCP_NODELAY`、会话超时与 LRU 回收、对 `EAGAIN` 的抖动容忍（以前一超时就断流，导致"不停重连却一直没画面"的死循环）；新增 `/ping` 心跳和板端自带预览页。`sdkconfig`：socket 数 10→16，开了 TCP keepalive。

## 顺手抓到一个 bug 并修了

复查时发现中继其实**已经死了一分多钟**：

```

```

根因：`camera_relay.py` 里负责读上游的线程是**一次性**的，断了就退出；而重启它的唯一入口是"有新观众进来"。所以一旦**板子掐断连接的那一刻没人看画面**，中继就永远停在 error 对外 503，刷新也没用——这正是你之前"摄像头不显示实时"的一部分原因。

修了三处：

| 改动 | 作用 |
|---|---|
| 断流后退避重连（1.6 倍递增，上限 6 秒） | 板子重启、WiFi 抖动都能自己恢复 |
| **看门狗线程**：每 2 秒检查"有人看但线程不在"就拉起 | 根治那一类死锁，不再依赖新观众触发 |
| 连续 12 秒解不出帧 → 判定断流并重建 | 光靠 TCP 超时要几十秒才报错，期间画面一直是死的 |
| `server.py` 首帧等待 8→15 秒 | 板子重启后要先连 WiFi 再起摄像头，8 秒不够会陷入"重连→没帧→再重连" |

`status` 接口新增了 `reconnects` 计数——以后一眼就能分清是"网络偶发抖动"还是"板子在反复重启"。
