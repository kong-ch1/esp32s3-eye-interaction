## 行为上的变化

| | 第 1 周 | 第 2 周 |
|---|---|---|
| **链路方向** | 单向:板子 → 服务器 → 网页 | **双向**:多了 网页 → 服务器 → 板子 |
| **网页的角色** | 纯旁观者 —— 刷新一百次也只能看到已有数据 | 能**主动指挥设备**再采一次 |
| **板子的角色** | 纯发布者,自己决定什么时候采 | 会**听指令**,按请求的参数采 |
| **采样节奏** | 固定 1 秒 1 条 | 定时上报仍是 1 秒 1 条;但收到指令会**突发采一批**(如 8 条 @120ms),不受 1Hz 限制 |
| **谁在追踪执行结果** | 没人 | 服务器有四阶段状态机:受理 → 下发 → 设备接收 → 完成 / 超时 |
| **数据能不能区分来源** | 不能,所有记录长得一样 | 能:`trigger='timer'/'command'` + `request_id` 精确关联到那次点击 |
| **失败能看出什么** | 只能看出"数据没了"(stale) | 能看出**卡在哪一段**:`accept`(板子没来取) / `exec`(取了没执行完) |

## ⚠️ 过程中发现并修掉一个会产出「假证据」的 bug

第一次真机测试时，事件显示**样本数 10、入库跨度 104839 ms**。根因：事件 id 用的是内存计数器，**板子一重启就归零**，两次不同时间按的 UP+ 生成同一个 id，被服务器按 id **误合并成一条**。

> **它产出的不是"没有数据"，而是看起来像证据、实际是错的数字。错的证据比没有证据更危险。**

修复：给事件 id 加上电随机前缀（`BTN-2a3613-…`）。另外在网页上加了防线 —— 跨度 >30 秒自动标红「事件 id 可能撞车」，让这类问题**自己在界面上暴露**。旧的 4 条污染记录我**故意留着**，正好当这个告警的实物样本。
