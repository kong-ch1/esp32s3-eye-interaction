## 这条为什么是第2周最硬的一条

任务卡在「后2学时」和「当堂验证」两处都写了它。它要证明的东西比页面上比数字强得多：

> **停掉 1Hz 周期上报之后，数据库里任何新增记录都只可能来自指令。**

但这里有个真问题：板子只做 POST、不监听端口，指令全靠"搭车"在它**自己上报请求的响应体**里下发 —— 上报一停，通道就断了。任务卡那句"**保持命令通道**"正是指这个矛盾。

解法是暂停期间把「上报数据」换成「心跳」：

```
正常：POST /api/data   写一条记录 + 取指令
暂停：POST /api/poll   不写任何记录，只为取指令
```

通道不断，而库里一条新传感记录都不会有。

## 真机验收结果（`tools/pause_acceptance.py`，全自动）

```
[1] 基线       3 秒内 +2 条         → 周期上报正常（作为对照）
[2] pause 指令 done，四段 980 / 1281 / 610 ms，端到端 2871 ms
[3] 暂停生效   6 秒内 +0 条         → 上报确实停了
               paused=True，心跳 0.73 秒前刚发 → 命令通道保持住了
[4] 暂停中点采集 done，新采集 7 条，端到端 4281 ms
[5] 关键断言   7 条新增 100% 是 trigger='command'，0 条 timer
[6] resume     done，3 秒内恢复 +2 条
```

**第 5 行就是任务卡要的那个证明**：周期上报停着，这 7 条不可能是页面翻出来的旧值。

## 顺手修掉一个会造成"冤假错案"的隐患

暂停期间读数不再增长，数据年龄必然变大。原来的逻辑只看年龄，会把它显示成「未更新 · 已 N 秒」—— 既冤枉了设备，又**掩盖了"暂停生效"这个事实**。现在三态分开：

| 状态 | 显示 |
|---|---|
| 暂停中 | 已暂停周期上报 · 心跳 N 秒前 |
| 正在恢复 | 正在恢复上报…（心跳仍在） |
| 真未更新 | 未更新 · 已 N 秒 |

另外指令类型加了白名单：拼错当场 400 并回可用类型，而不是受理一条板子永远不认识的指令、白等 30 秒超时。
