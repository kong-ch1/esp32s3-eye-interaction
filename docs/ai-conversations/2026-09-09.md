最后讲讲那个“停采就提示未更新”是怎么做到的，这里有个很多人误解的点：

- 板子断电 → 数据库里最新那行的时间就再也不动了
- 网页再问 → 服务器照实回答“最新那条，它的年龄是 3 秒、8 秒、20 秒……”
- 年龄超过阈值 5 秒 → 服务器顺手打上 `stale: true`，网页据此变红显示“未更新”

也就是说，**“未更新”是网页自己算出来的**，不是谁通知它的——这反而更能证明数据真的来自一台会停掉的设备，页面里没有写死的数值。

## 三个实战经验，省得你踩坑

**① 别把原始数据整坨丢给模型。**

**② 答案必须短。** 设 `num_predict` 限制在 200 token、`temperature=0`。稳定性优先，别让它自由发挥。

## 先回答你最担心的：AI 方案会让板子崩吗？

**不会，因为固件一个字都不用改。** 前面说的 `/api/ask` 是**加在你电脑上**的东西——板子依旧每秒只干它现在干的那件事：发一个 200 字节的 JSON。大模型跑在你的 GPU 上，读的是 SQLite 里的数据，跟 ESP32 没有任何直接接触。板子的内存占用**一字节都不增加**。

## 你之前崩溃的真正原因（查了你的 sdkconfig）

不是 ESP32 太弱，是两个配置吃亏了：

**① 8MB PSRAM 一直在睡大觉**
sdkconfig 里写着 `# CONFIG_SPIRAM is not set`。你这块 S3-EYE 板载 **8MB 外挂 PSRAM**，硬件焊好了、白白在那儿，但固件没启用它。结果你就只有内部 SRAM 那点地方可用——相当于买了 512G 的电脑，只让你用 C 盘。

**② HTTP 上报跑在只有 3584 字节的任务栈上**
`CONFIG_ESP_MAIN_TASK_STACK_SIZE=3584`，而 main.c 里**没有创建任何独立任务**——初始化 WiFi、读 IMU、跑 `esp_http_client` 全挤在 `app_main` 这一个任务里。WiFi 事件回调 + TCP 收发 + JSON 拼装，随时可能把 3.5KB 捅穿。现在没崩是因为每秒只发一条、时机刚好错开；你一加功能，它就炸。

## 关键认知：崩溃其实有两种病，治法完全不同

| 症状（串口打印） | 病因 | 解决方向 |
|---|---|---|
| `Stack canary / Stack overflow` | **栈**不够——局部变量、函数嵌套太深 | 加大任务栈 / 把活挪到新任务 |
| `malloc failed / heap caps alloc` | **堆**耗尽——缓冲区太大、没释放 | 开 PSRAM / 大缓冲放外部 RAM |
| 反复重启无报错 | 看门狗饿死——某段代码卡太久没喂狗 | 加延时、降优先级、拆任务 |
